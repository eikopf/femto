# Independent coordinator and peer qualification

The current fixture covers coordinator registration, transport, TLS and OPDS acquisition. The custom sync protocol and its fixture stages have been removed. Dated evidence below records the earlier source revisions, including the removed stages.

The [three-packet loss qualification](../tests/evidence/transport-burst-loss-2026-11-08.json) passes against Headscale 0.29.7 and official Tailscale 1.104.5 on direct and relay-only paths. Each path drops three 1,312-byte payload packets within 11 ms after two authenticated session installations, with no additional packet drops. Both deliver 65,536 exact bytes in each direction and close orderly after more than 195 seconds. Relay traffic sends no direct UDP packets. The complete control, UDP, TLS trust/truncation, OPDS, progress, and journal suite also passes. All 391 recorded inputs remain unchanged. An initial fixture attempt incorrectly required three payloads in one poll; its injection failure and log are retained. This does not resolve the earlier unrelated direct TCP timeout or qualify other loss patterns and physical hardware.

The [transport-data-loss qualification](../tests/evidence/transport-data-loss-2026-11-08.json) adds one outbound encrypted data-packet loss after WireGuard renewal in both TCP modes. Each run discarded a 1,312-byte packet with two sessions installed, 49,152 application bytes accepted, and 45,056 bytes echoed. Relay-only TCP then completed exact 65,536-byte transfers in each direction over 195.193 seconds; direct TCP did so over 195.059 seconds. Both closed orderly, and relay-only mode sent no direct UDP packets. The existing initiation/response-loss preflight also passed, with recovery in 25.901 seconds over DERP and 15.598 seconds over direct UDP. The complete coordinator, UDP, TLS trust/truncation, OPDS, progress conflict/race, and reader-journal sequence passed with all 381 recorded inputs unchanged. This run includes the bounded state serializer and journal startup changes. It does not qualify burst or inbound loss, reordering, relay migration/failover, NAT traversal, or physical Picco behavior. The earlier unexplained direct TCP stall remains unresolved.

The [DERP response-loss qualification](../tests/evidence/derp-response-loss-2026-11-08.json) extends the fixture to discard one initiation and one response in each TCP mode. Relay-only timer recovery took 25.472 seconds, followed by a 195.190-second TCP connection with 65,536 exact bytes in each direction, two authenticated session installations, orderly closure, and no direct UDP output. Direct recovery took 10.483 seconds, followed by a 195.062-second connection with the same payload, installation, and closure checks. The complete control, UDP, TLS trust/truncation, OPDS, progress conflict/race, and reader-journal sequence passed. All 381 recorded source/configuration/fixture inputs remained unchanged. Workspace Clippy, formatting, and Python syntax checks also passed. This fixture change adds no production loss hook. The earlier unexplained TCP stall, transport-data loss, relay migration/failover, NAT traversal, and physical Picco qualification remain unresolved or unqualified.

`./scripts/check-headscale` builds and runs the local coordinator probe in `nix/headscale.nix`. The existing Nix lock pins Headscale 0.29.7, Tailscale 1.104.5, and OpenSSL. The command creates a temporary CA, server certificate, SQLite database, user, reusable preauth key, and femto identity. Coordinator and echo-service listeners bind to loopback, the admin sockets stay inside the temporary directory, and update checks and external DERP-map fetching are disabled. The fixture configuration follows the pinned [Headscale configuration example](https://github.com/juanfont/headscale/blob/v0.29.7/config-example.yaml). The directory contains one region resolving `localhost` over IPv4 to the fixture HTTPS port, with IPv6 and client STUN disabled. Headscale's embedded DERP server runs on that HTTPS listener with registered-client verification enabled. Its required STUN listener binds an ephemeral loopback port and is not advertised to clients. The fixture supplies no external relay regions.

The probe uses femto's Rust TLS, bootstrap, Noise/HTTP2, registration, rotation, journal, and coordinator-map code. Its fixture CA is passed to the existing explicit-root TLS connector. Production trust configuration is unchanged. A separate untrusted CA must fail with an issuer-validation error before the probe creates an identity.

The positive run registers one node, receives an authenticated map, and obtains an authorized IPv4 address. A second process reopens the identity without an auth credential and keeps an authorized map stream open. After that process reports map readiness, the runner expires the node through Headscale's admin API. The stream must deliver an authenticated local-node update with the exact node key and `Expired: true`. The coordinator must reject that update with `MapError::Node`, and the stream must lose local-address authorization. A timeout or connection closure alone fails this check. A separate process attempts registration with the existing node key and no auth credential. It must receive `Expired`, retain no session authorization, and reject a map request with `PermissionDenied`. The runner verifies that this refusal leaves the identity record unchanged and does not create a rotation journal.

The renewal process reopens the same store, persists a replacement node key, registers the old/new key relationship with the fixture's reusable preauth key, commits the journal, and obtains another authorized map. Headscale's admin API must report exactly one node with the same node ID, machine key, and assigned addresses. Its active node key must agree with femto after each registration and change across renewal. The registration and renewal run in different processes, so the probe also exercises durable identity reopening.

After renewal, the reconnect probe opens the existing identity without an auth credential and starts the reusable host reconnect controller, shared control worker, and reconnect pump. After the initial map authorizes an address, the endpoint publisher sends the documentation-range endpoint `192.0.2.1:41641` over a separate verified control connection. The runner kills Headscale only after the server acknowledges that publication. The probe must deny network-operation access while disconnected before the runner restarts Headscale with the same temporary database and keys. A replacement worker repeats verified TLS bootstrap, Noise/HTTP2 setup, registration without an auth credential, and a fresh full-map request. The new map must authorize the same address. The replacement publisher then sends `192.0.2.2:41641` and must receive a successful authenticated response. These synthetic endpoint addresses are not contacted. Peer-side propagation of the updates is not checked. The identity/timestamp record must remain byte-for-byte unchanged during reconnection, and Headscale must retain the node ID, machine key, node key, and addresses. The replacement worker must join during shutdown. This check uses the same `host_reconnect::Controller` as the CLI with the fixture trust root supplied through its authenticated setup factory. It exercises publication-worker replacement. It does not exercise the Picco TLS adapter, a connected DERP relay or pending relay dialer, the complete CLI command, or application-request recovery.

After renewal, a new stream remains open while a second femto identity registers. The original stream must receive `PeersChanged` and authorize the exact new public node key. The runner deletes the second node through Headscale's admin API. The stream must receive that node's ID in `PeersRemoved`, revoke its route, and retain the original node's local-address authorization. Both clients in this phase use femto. This phase establishes coordinator update behavior; its packets do not cross a network transport.

Before peer deletion, the probe opens the second fixture identity after its registration process releases the store lock. The two fixture identities perform a WireGuard handshake inside the probe process. The live coordinator authorizes the installed session and incoming UDP packets to port 1234. One decrypted packet remains queued. The runner updates the temporary database policy through Headscale's admin API to permit only UDP port 1235. The stream must deliver a policy update while retaining the peer and local authorization. The data plane must refuse release of the queued packet and deny a fresh encrypted packet to port 1234. A fresh packet to port 1235 must still decrypt and reach the release boundary unchanged through the same session. This checks selective revocation using real coordinator policy, including the application delivery boundary; it does not exercise UDP transport, an independent WireGuard implementation, or the application TCP stack.

After the coordinator checks, the runner replaces its temporary policy with an allow-all policy and starts the pinned official `tailscaled` in [userspace networking mode](https://tailscale.com/docs/concepts/userspace-networking). Its state directory and control socket are private to the fixture. Log uploads and port mapping are disabled. DNS, route acceptance, and netfilter configuration are disabled. The fixture CA supplies TLS trust for the local coordinator. The peer registers with the temporary auth-key file as `femto-independent-peer`. A Python UDP echo service binds an ephemeral loopback port. Femto reopens its existing identity without an auth credential, requests a fresh map, resolves `femto-independent-peer.femto.test`, and sends one bounded request through its ordinary controlled network owner, discovery, handshake, UDP binding, and nonblocking transport. The runner requires exactly one matching plaintext request at the local service and the exact echoed payload at femto. The Rust probe installs no relay adapter. Encrypted direct datagrams can use the host's interface addresses; the entire check is not loopback-only. This establishes one direct IPv4 UDP exchange with an independent WireGuard implementation under a permissive fixture policy. It does not qualify NAT traversal, restrictive UDP reply policy, DERP, sustained traffic, rekey, or physical Picco behavior.

A subsequent TCP phase replaces the fixture policy with one rule permitting the femto address to reach the official peer's ephemeral TCP service port. The input policy contains no reverse ephemeral-port rule. A fresh femto process reopens its identity, registers without an auth credential, and obtains the new authenticated map. Its managed TCP connection uses the same name resolution, control-worker authorization boundary, WireGuard handshake, and direct UDP poller. The probe sends a deterministic 65,536-byte sequence in 4096-byte portions released every 13 seconds. The connection must remain active for at least 195 seconds, beyond the original WireGuard session's 180-second lifetime. The probe requires at least two authenticated session installations. It records separate initiator and confirmed-responder counts, since either peer can initiate renewal. Raw incoming handshake-response counts remain diagnostic evidence. These checks require renewal and continued application traffic on the same TCP connection. The loopback service verifies the sequence and echoes it in reads of at most 997 bytes, then shuts down its write side. Femto verifies all returned bytes, requires remote EOF only after the full transfer, closes its write side, and waits for the TCP state to reach Closed. The service also requires client EOF. This exceeds the stream's 16 KiB send and receive buffers and checks segmentation, partial I/O, and orderly bidirectional shutdown against the official peer's independent TCP implementation. It does not exercise the blocking stream adapter, TLS, HTTP, catalog acquisition, transport-data loss, or concurrent flows.

Before opening TCP in both direct and relay-only modes, the probe requests one session and deliberately discards its first outgoing 148-byte WireGuard initiation at the egress callback. Subsequent iterations only pump transport and inspect authenticated session-installation counters. They do not request another session or open a TCP connection until an initiated session completes. Both modes also discard the first incoming 92-byte WireGuard response before passing it to the authenticated network owner. Direct mode uses a fixture-only UDP pump. Relay-only mode polls a verified, authorized DERP connection and discards that response event, then transfers the same connection into the ordinary relay pool without reconnecting. Other packets retain the network owner's authorization checks. The relay fixture rejects nonempty health reports and restart events during this preflight; relay failure recovery is not tested here. After the injected response loss, both modes resume their ordinary pollers. Production packet handling has no response-loss hook.

Recovery must take at least ten seconds after the initial initiation drop in each mode. The stage result records both drop counts, the response-drop timestamp, timer-only recovery, and elapsed milliseconds; the Python runner requires those fields before accepting the TCP result. Preflight has a 90-second deadline from the discarded initiation, matching the bounded retry-series lifetime. The listener allows 100 seconds for connection setup, and the Rust probe has a 330-second overall deadline. TCP service reads retain their 20-second timeout. Failure reports retain the received byte count and Rust probe diagnostics. This isolates automatic handshake retry from application-driven readiness. The established connection also receives the transport-data loss injection described below. Relay migration remains outside this scenario. Earlier saved qualification runs retain their original loss-injection scope.

After at least 49,152 bytes have entered the TCP socket and at least two authenticated sessions have been installed, the fixture drops the next three outgoing WireGuard payload packets. It selects transport type 4 with ciphertext longer than 256 bytes, excluding keepalives and header-only acknowledgments in this single-flow fixture. Before each ordinary transport poll, it drains the bounded outgoing queue until the payload-drop count reaches three. Any other packets discarded during this interval are counted separately. TCP output generation resumes later in the loop, so injection can span successive polls. The report records every selected packet's timestamp, ciphertext size, accepted and echoed byte counts, and session-installation count. The Python runner requires all three drops after renewal and before the full echoed payload, followed by exact complete delivery and orderly shutdown. No production packet handling is changed. Inbound loss, arbitrary loss rates, reordering, relay migration, and loss at the exact key-installation boundary remain unqualified.

The TLS phase uses `ThreadShared<FixtureDriver>`, the portable blocking TCP adapter, and `host_tcp_tls::Connector` with the fixture CA. The fixture driver keeps application operations inside the controlled network owner and polls the shared transport implementations. A Python OpenSSL-backed TLS server listens behind the same official peer. Each case gets a fresh authenticated map under a policy limited to that service port. The valid case negotiates HTTP/1.1 through ALPN, verifies an exact GET request, and returns a deterministic 64 KiB HTTP body. Femto reads through the production TLS adapter until clean TLS EOF and verifies the complete response. Separate cases present a valid certificate for the wrong hostname, a matching-name certificate signed by an untrusted CA, and a complete response followed by TCP closure without TLS close-notify. The first two require the specific certificate-validation errors before any HTTP request is accepted. The truncated response requires UnexpectedEof even though its HTTP body is complete. Each TLS case runs over both a direct connection and a relay-only connection. The relay-only driver creates no UDP socket, completes authenticated relay setup before application I/O, and uses bounded nonblocking relay polling during application I/O. The valid relay case requires incoming relay events and zero direct UDP sends. These checks exercise independent TLS interoperability and the blocking adapter over both enrolled transport paths. They use an exact raw HTTP fixture rather than the catalog HTTP parser, OPDS acquisition, credentials, or progress-sync protocol. The TLS server version is recorded in the report.

Before the direct transport checks, a separate femto process reopens its enrolled identity, obtains a fresh authenticated map, and exchanges one UDP echo with the official peer through the embedded DERP server. It uses the ordinary controlled network owner, WireGuard sessions, UDP request API, and authorized relay pool. Relay setup uses the fixture CA and verifies the `localhost` certificate name. The probe creates no UDP transport; its direct-output callback returns `WouldBlock` without sending. A successful reply therefore requires the relay path. The runner checks exactly one expected plaintext request and response, positive relay event/output counts, and joined control-worker shutdown. This qualifies one encrypted UDP exchange through an independent relay and peer implementation. It does not qualify relay failover, path migration, or Picco operation.

The next probe exchanges a 64 KiB TCP echo through the same relay-only pump. Femto creates no UDP transport. The fixture policy permits only the client-to-server TCP destination, and the server receives plaintext through official Tailscale userspace networking. The client compares every returned byte, requires remote EOF after the complete echo, closes its socket, and waits for the closed state before joining its control worker. The runner also checks that the peer receives EOF. This qualifies bidirectional TCP and orderly shutdown over DERP under a destination-only policy. The transfer sends 4096-byte increments every thirteen seconds and lasts at least 195 seconds. The handshake owner must report at least two authenticated session installations. The relay pool also records accepted WireGuard responses, but peer-initiated renewal can complete without an incoming response. The same TCP connection therefore remains usable after demand-driven renewal and beyond the original keys' expiry. The shared direct/relay fixture refreshes its monotonic clock after potentially blocking relay setup. The TLS cases also run over DERP. The OPDS and progress service checks also run over direct and relay-only paths.

The application phase runs `femto`'s `headscale-services` example against a Python HTTPS OPDS service behind the official peer. Each application check runs once over direct transport and once in relay-only mode, with separate output paths and fresh server-side progress records. The examples share `femto-microlink/examples/support/transport.rs`, which keeps network operations inside the controlled owner. Relay-only setup verifies the fixture relay certificate before application I/O; the application pump uses the existing authorized relay pool and creates no UDP socket. The result requires incoming relay events, zero direct UDP sends, and joined control-worker shutdown. The catalog transport uses its single-thread `Shared` adapter around `ThreadShared`, allowing the fixture to inspect transport counters and join the owner after all application streams are dropped. The example reopens the enrolled identity, obtains a fresh authenticated map, and constructs `tailnet::Tailnet` with the fixture-root TLS connector. It first requires HTTP 401 without credentials. The authenticated request follows a same-origin redirect and parses a chunked OPDS 2 feed with a self link and one publication. The acquisition link resolves relative to the final feed URL. The example calls the existing CLI acquisition selection and `AcquisitionFile::receive` implementation from `catalog.rs`. That code streams the EPUB into temporary storage, flushes it, opens it through the shared reader, reads its first chapter, and publishes it without replacing an existing path. Both the example and runner compare the resulting file with the 220,069-byte fixture. A second acquisition preparation must refuse the existing destination. The server requires the ephemeral Basic credentials on every successful request and checks exact counts for refusal, redirect, feed, and book requests. This qualifies the library catalog transport, parser, and CLI acquisition implementation over both enrolled direct and relay-only TLS paths. It does not run the complete `tailnet-connect` command, interactive browsing, or the Picco UI.

The command writes a credential-free report to `output/headscale-probe.json` only after all checks succeed. A new run removes the previous report first. The report records the server version, capability version, verification time, and checked behavior. Both server processes are terminated and temporary credentials, private keys, identity records, and database are removed on exit. The diagnostic prints only stage results, assigned test addresses, and public node keys.

## Direct-to-relay path migration

Run `FEMTO_HEADSCALE_MIGRATION_ONLY=1 ./scripts/check-headscale` for the independent path-migration fixture. It creates a temporary coordinator, enrolls a femto identity and the official Tailscale peer, and runs one TCP echo connection under a destination-only policy. It writes `output/headscale-migration.json` only after success. The ordinary command retains the control, direct/relay, TLS and OPDS fixture.

The migration pump uses the production controlled network owner, authenticated discovery, route selector and relay pool. For the first forty seconds after TCP establishment, UDP remains available. From forty through one hundred seconds, every direct send returns `NetworkUnreachable` and every received UDP datagram is discarded. The verified relay stays available. UDP is then restored. The fixture requires nonempty authenticated direct transport traffic in both directions before and after the outage, no accepted direct traffic during it, relay events and queued packets during it, and advancing echoed application bytes during the outage. One TCP handle and one server-accepted connection span all phases.

The existing handshake initiation/response loss, post-renewal three-packet loss, exact 65,536-byte echo, minimum 195-second lifetime, two authenticated session installations and orderly-close checks remain enabled. The migration service read timeout is forty-five seconds to permit the injected outage transition; ordinary TCP checks retain twenty seconds. The fault is injected in fixture I/O, not in production packet handling. This qualifies the selected simulated direct-path failure and recovery, not real NAT traversal, a WAN outage, relay-server failover, or physical Picco networking.

The [transport lifecycle checkpoint](../tests/evidence/transport-lifecycle-2026-11-08.json) records an echoed-byte increase from 16,384 to 32,768 during the outage, direct recovery, and full transfer completion. It also records 74,237 failed direct sends before the discovery-probe fix and 46 afterward. Definitively failed probes now leave the output queue; scheduled fresh attempts and `WouldBlock` retention remain. The two counts are measured fixture results, not universal bounds. The standard independent interoperability suite also passes with the fix enabled.
