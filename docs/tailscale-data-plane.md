# Tailscale data-plane integration

`femto_microlink::plane::DataPlane` owns the typed peer directory, receive policy, and active WireGuard sessions. It has one mutable owner. The shared `network::Network` owner routes direct UDP and DERP packets through this API.

## Control updates

`apply_update` accepts full or incremental peer upserts/removals and the coordinator map bytes used by the policy parser. The caller must first authenticate the coordinator message, decode its node schema, and translate peer key-expiry times to monotonic deadlines. The `coordinator::Coordinator` adapter now supplies bounded JSON translation and expiry conversion. Transport authentication remains the caller's responsibility.

Full updates replace the directory and start policy from default denial. Delta updates preserve omitted peers and policy fields. Peer keys and addresses must be unambiguous. Each update is validated in temporary state before installation. Duplicate keys, conflicting removals/upserts, duplicate addresses, local-address ownership, invalid policy, and capacity overflow clear all sessions and authorization. A delta cannot recover from this failure; a full update is required.

The directory is configurable up to 256 peers and four exact IPv4 addresses per peer. Prefix routes and subnet routing are not accepted by the typed model. Active-session capacity is configured independently. Changed peer records discard their sessions; unchanged records can retain sessions while policy is checked on every packet. Expired peers cannot start handshakes or exchange packets. Monotonic clock rollback clears authorization.

## Jailed peers

`Peer::jailed` carries the coordinator node's `IsJailed` flag through full `Peers` and incremental `PeersChanged` records. Omission means false; malformed values reject the map and clear authorization. A changed flag invalidates sessions and pending plaintext with the rest of the peer record. The [pinned Tailscale node schema](https://github.com/tailscale/tailscale/blob/v1.104.5/tailcfg/tailcfg.go#L513-L516) permits connections to jailed peers while prohibiting connections initiated by them. Femto applies this restriction even when an ordinary receive rule would allow their traffic. Managed outgoing TCP and UDP connections retain the reply paths described below. A local node marked jailed is currently rejected, because restricted local initiation is not implemented. `PeersChangedPatch` has no jailed flag in that schema.

Host regressions cover initial and replacement node records, queued-packet revocation, malformed flags, TCP reply leases, UDP deadlines and capacity, socket closure and reuse, and encrypted UDP exchanges. These tests do not establish live coordinator delivery of jailed-node changes or physical Picco behavior.

## Handshake and packet ownership

`begin_handshake` returns an opaque permit for a known, unexpired peer. `install` consumes that permit and a session authenticated to the same peer by the managed handshake owner. It rejects expired sessions and permits from an earlier authorization state. The handshake owner must bind the cryptographic peer identity to the permit; the session wrapper cannot independently infer that identity from its symmetric keys.

Every accepted map update and disconnect replaces a private reference-counted authorization marker. Handshake permits and pending plaintext retain the previous marker. Identity comparison prevents their use after an update and across different data-plane instances. This avoids a generation-counter collision after object replacement. Markers are in-memory objects and are not serialized.

`receive` authenticates and decrypts the WireGuard packet, validates supported IP/transport structure, checks that its source belongs to the authenticated peer, requires the local destination address, and applies receive policy. Empty keepalives return no application packet. Successful application data remains opaque in a `PendingPacket`. `release` consumes it at the application-stack boundary, checks its authorization marker, peer expiry, source ownership, and current policy, then returns bytes. A queued packet cannot retain authorization after peer removal or policy replacement.

TCP, UDP, and ICMPv4 are supported for policy inspection. IPv4 options, fragmentation, reserved fragment flags, truncated transport headers, and mismatched UDP lengths are rejected. Packet parsing reuses the pinned protocol crate with additional structural checks. The attached smoltcp TCP stack and UDP codec validate IP and transport checksums at their application boundaries.

`send` validates the local source and selected peer's destination address before encrypting. It does not use receive policy as an egress ACL. The network owner binds queued ciphertext to authorization and session identity and rechecks delivery permits before output. Managed outbound TCP connections accept validated replies through their connection state. Managed UDP sockets accept checksummed replies from the exact peer and address/port tuple for 30 seconds after an outbound datagram enters the ciphertext queue. The data plane retains at most 32 UDP reply tuples; another outbound datagram to the same tuple refreshes its deadline. Incoming traffic does not refresh it. Closing a socket, disconnecting, or changing peer authorization or receive policy revokes its reply permissions. Harmless map updates preserve UDP tuples but invalidate queued plaintext. Raw IP sends do not create UDP reply permissions. Other incoming traffic requires an explicit matching receive rule.

`disconnect` clears peers, policy, and sessions and invalidates pending packets and handshakes. The runtime must separately cancel sockets, control requests, discovery, relay writes, and pending jobs. The integrated owner supplies receiver-index dispatch, handshake replay state, bounded queues, and one previous receive session during key renewal. Host and Picco runtimes connect the identity/timestamp stores to the handshake owner; Picco uses an NVS backend. Reconnect repeats authorization before application access resumes. Physical NVS power-loss behavior, trusted device time, and sleep/reconnect operation remain unqualified.

## Verification

Host tests use encrypted local pairs from the pinned Rust WireGuard implementation. They cover permitted packets, replay rejection, forged source/destination/port fields, malformed transport structure, keepalives, outbound address checks, policy replacement on live sessions, full-update omission, peer removal during a handshake, queued-plaintext revocation, cross-instance token rejection, queued expiry, capacity reclamation, malformed maps, clock rollback, and disconnect. These tests do not establish interoperability with Tailscale, DERP, or an independent WireGuard implementation.

## Coordinator stream framing

`control_stream::MapStream` consumes the four-byte little-endian length framing used by the pinned coordinator protocol implementation. It retains one frame with a 64 KiB body bound, matching the receive-policy input limit. It checks the declared size before allocating a body, uses fallible allocation, and handles arbitrary header/body fragmentation. A large input chunk does not cause an equally large internal copy or a queue of decoded maps. The handler receives each borrowed body synchronously in wire order and must validate and apply it before returning.

Zero-length frames, oversized frames, truncated EOF, and handler rejection permanently close the decoder. Later frames in the same input are not delivered after an error. Earlier successful handler calls remain applied; the owner must invalidate its data plane when the stream fails. EOF also closes a successfully completed stream. A new connection requires a new decoder and full synchronization. Session resumption is not implemented.

`read_maps` drives the decoder through `std::io::Read` with a 2 KiB ingress buffer. It checks cancellation before reading and after a successful read, retries interrupted reads, and propagates other I/O failures. The platform reader must enforce a finite read deadline because cancellation cannot interrupt a blocking read. The caller must disconnect authorization after any return, including orderly EOF. Authentication, HTTP status and body decoding, HTTP/2, peer-node schema handling, and clock translation are not provided by this adapter.

Compression must remain disabled. The [Tailscale request schema](https://github.com/tailscale/tailscale/blob/main/tailcfg/tailcfg.go) defines an empty `Compress` value as uncompressed; the pinned Rust request serializer does not request compression. The decoder does not infer or decompress compressed bodies. Host tests cover every split in a multi-frame input, bytewise delivery, maximum-sized frames in a multi-megabyte input, malformed lengths, truncated EOF, handler failures, cancellation, interrupted reads, and a local TCP connection ending mid-frame. The TCP fixture supplies synthetic response-body bytes; it does not exercise coordinator authentication or live service interoperability.

## Coordinator node adapter

`coordinator::Coordinator` owns a data plane and a bounded node-ID directory. `apply` accepts an authenticated JSON response and a simultaneous trusted Unix/monotonic clock pair. It translates `Node`, `Peers`, `PeersChanged`, `PeersRemoved`, and key/key-expiry fields in `PeersChangedPatch`. The node-ID directory preserves identity across key replacement and translates ID removals to key removals. Each update validates temporary directory state before applying peers and policy together. An error clears both the directory and data-plane authorization.

The initial map requires the configured local key and IPv4 address in an authorized local node. A first map with no peers initializes an empty directory. Later nonempty `Peers` lists replace the directory; an empty or omitted list permits deltas. Replacement lists take precedence over changed/removed fields, and patches apply afterward. Replacement peer lists preserve omitted policy within a synchronized stream. A new stream begins with default-deny policy. Duplicate node IDs, duplicate keys, conflicting delta operations, excessive counts, and invalid policy disconnect the adapter. Patches for unknown node IDs are ignored, as specified by the coordinator schema. Duplicate recognized JSON fields are rejected by Serde.

The map byte limit is 64 KiB. The directory limit is at most 256 records, including records that cannot currently exchange traffic. A record accepts at most eight assigned address prefixes and retains at most four IPv4 host addresses. IPv6 host addresses are recognized but do not enter the IPv4 data plane. `AllowedIPs`, when supplied, must explicitly include an assigned IPv4 host address for that address to be installed. Subnet and exit routes do not grant additional addresses. Missing machine authorization, explicit expiry, and unsigned-peer-API-only status prevent traffic authorization. The adapter also retains discovery keys, endpoint lists, home relay-region hints, and peer names. Capability metadata is not yet integrated.

RFC 3339 expiry parsing uses pinned `time` 0.3.44. Missing expiry and the exact Go zero timestamp mean no key deadline. Other timestamps convert to monotonic deadlines; elapsed timestamps expire immediately. The local node deadline caps every installed peer deadline, so packet and handshake checks also enforce local expiry. Key-expiry patches can change peer deadlines. Backwards clocks or a wall/monotonic elapsed-time discrepancy over one second disconnect authorization. A forward clock step records the new clock pair and requires full resynchronization. The caller must supply trusted time; the adapter does not establish RTC or network time.

`read_stream` connects the bounded framing adapter to JSON application and disconnects on EOF, cancellation, or error. It is a synchronous body-processing helper, not a concurrent network actor. The runtime can instead call `apply` from its authenticated stream events and use `data_plane` for packet operations. Runtime code must not bypass the coordinator with direct typed map updates or data-plane disconnect calls. Peer changes, expiry, and policy parsing follow the [Tailscale node and map schema](https://github.com/tailscale/tailscale/blob/main/tailcfg/tailcfg.go); the separate host transport probe verifies a live Noise connection. The host stream guard now connects HTTP/2 map events to this adapter; enrolled live-map testing remains unfinished.

Host tests cover ID-based replacement/removal, key and expiry patches, local expiry, withdrawn authorization, unsupported routes, duplicate fields, clock steps, stream EOF, full-map recovery after errors, and unknown patch handling. An encrypted Rust WireGuard pair checks that peer-list replacements preserve omitted policy, empty lists preserve peers, and policy revocation invalidates both queued plaintext and subsequent packets. These tests do not establish a live coordinator session.

## Peer routes and names

Each coordinator record retains at most 16 deduplicated direct UDP endpoints, an optional discovery key, a home relay-region hint, and a canonical ASCII name. Endpoints must be numeric socket addresses with a nonzero port. Unspecified, loopback, multicast, and IPv4 broadcast destinations are rejected, including IPv4-mapped loopback addresses. Both IPv4 and IPv6 underlay endpoints can be retained; the application data plane remains IPv4-only. Endpoint presence does not establish reachability or authenticate a peer.

A full node replacement replaces its route metadata. A nonempty endpoint patch replaces endpoints; an empty or omitted patch preserves them. Nonzero `DERPRegion` patches replace the home region. `HomeDERP` takes precedence over the legacy `127.3.3.40:region` field in a node record. Discovery-key patches replace the key, with the zero key represented as unavailable. Route metadata follows node IDs across node-key rotation. The relay directory supplies server hostnames and certificate expectations; live connections remain unfinished.

`route` returns a borrowed route only while the data plane authorizes that peer. `resolve` matches canonical peer names and returns the current node key and first installed IPv4 address. Matching ignores ASCII case and one trailing dot. Names are bounded to 253 bytes, with DNS labels of at most 63 bytes. Ambiguous active names return an error. Short-name expansion, search suffixes, external DNS, and Unicode conversion are not provided; ASCII punycode names are accepted. Local expiry, peer expiry, removal, and disconnect prevent lookup results. Monotonic rollback during lookups disconnects authorization.

The lookup result does not authorize future packet delivery. Callers must still pass handshakes and traffic through the current data plane and discard stale transport work on map changes. Tests cover endpoint replacement and empty patches, discovery-key clearing, legacy relay hints, rotation, removal, exact name matching, ambiguous names, expiry, rollback, and malformed route metadata. Direct sockets, discovery exchanges, relay selection, and application socket integration remain unfinished.

## Relay directory

Coordinator `DERPMap` updates feed a validated relay directory in the same transaction as peer and policy state. Omitted or null `Regions` preserves the directory. A non-null region map replaces it, including an empty map that removes all regions. Invalid relay data disconnects authorization and clears the directory. The implementation does not merge hardcoded default servers, so it uses only the coordinator-supplied regions. Home scoring parameters are ignored until home-region selection is implemented.

Limits are 64 regions, eight servers per region, and 256 servers overall, within the existing 64 KiB map limit. Region IDs accept positive integers through the largest exactly representable JavaScript integer, matching the [coordinator DERP schema](https://github.com/tailscale/tailscale/blob/main/tailcfg/derpmap.go). Map keys must match region records, and node region IDs must match their parent. Region keys and global node names must be unique. Server order is retained. The shared relay scheduler excludes STUN-only servers and prohibited home regions.

Each server has a dial hostname, certificate expectation, independent IPv4/IPv6 address modes, TLS port, and optional STUN port. Certificate expectations represent either a verified name or the exact SHA-256 of a DER certificate. Fixed addresses do not replace the expected certificate identity. TLS defaults to port 443; STUN defaults to 3478 and accepts -1 to disable it. Empty address overrides request DNS; non-address overrides disable that address family. Insecure test flags and STUN test-address overrides are rejected. DNS names and literal addresses are validated; loopback, unspecified, multicast, and IPv4 broadcast literals are rejected.

`relay_for` returns the authorized peer's current region description. It does not select a server, open a socket, verify a certificate, or establish a DERP session. Callers must exclude STUN-only servers from relay connections and revalidate current map state before connecting or sending. Host tests cover identity/dial-address separation, defaults, explicit ports, raw certificate pins, duplicate records, bounds, replacement semantics, ordered servers, large region IDs, and transactional failure. Local host TLS handshake tests and a public-relay probe are implemented; relay failover and device interoperability remain unfinished.

## Host TLS transport

On Unix hosts, `host_tls::TlsConnector` establishes TLS over a resolved TCP address. It uses Rustls 0.23.46 with Ring and TLS 1.2/1.3, plus the compiled Mozilla roots from `webpki-roots` 1.0.11. A separate constructor accepts an explicit root store for private services and tests. The resolver and address-selection policy remain external. ESP-IDF does not compile this adapter; the device TLS adapter remains unfinished.

The server name sent in SNI is separate from the expected certificate name. Named certificates use Rustls WebPKI validation for the trust chain, name, validity period, and certificate constraints. An authenticated coordinator's raw-certificate fingerprint instead requires an exact SHA-256 match over the leaf DER certificate; that mode deliberately replaces PKI name, chain, and validity-period checks, as needed for pinned self-signed relay certificates. Both modes verify TLS handshake signatures through Rustls's cryptographic provider. There is no accept-any-certificate path. Session resumption is disabled, so each connection performs the configured verification. Public roots require a dependency update and rebuild when the bundled trust set changes; OS trust customization and revocation feeds are not integrated.

`connect_relay` uses the directory's hostname and certificate expectation. It checks the supplied numeric address against any fixed override, disabled address family, TLS port, and STUN-only status before opening TCP. A DNS-mode address must be supplied by the caller's resolver. The caller remains responsible for checking current peer/map authorization before starting transport work. The returned private stream implements `Read` and `Write` and can feed the protocol codecs. A verified TLS connection is not evidence of DERP enrollment or a live tailnet session.

The configured positive timeout is capped at 60 seconds. TCP connection and TLS handshake share one deadline. Each subsequent read, write, or flush gets a fresh operation deadline; repeated calls do not have a combined request deadline. Socket waits poll cancellation at intervals of at most 100 ms. Cancellation during the initial blocking TCP connect can take up to the configured connect timeout. An I/O error or cancellation poisons the stream. Clearing the cancellation flag cannot revive it. Rustls's outgoing buffer limit is 16 KiB; total TLS heap use has not been measured for device suitability.

Local TCP/TLS fixtures exercise TLS 1.2 and 1.3 with generated certificates. They verify successful encrypted exchange, wrong-name rejection, untrusted-root rejection, expired-certificate rejection, exact-pin success and mismatch rejection, separate SNI, poisoned-stream behavior, stalled-handshake deadlines, cancellation, and relay-target constraints. These tests use Rustls at both ends and do not establish live coordinator/DERP interoperability or ESP-IDF behavior.

## Bounded DERP session

`derp::RelaySession` wraps the pinned Rust DERP client over a `DeadlineIo` transport. `TlsConnector::connect_derp` connects the selected relay address with certificate verification, constructs the HTTP authority, and completes DERP setup. The session is returned only after the HTTP upgrade, server-key greeting, encrypted client information, and authenticated version-2 server information succeed. The portable constructor requires an already-authenticated transport; it does not authenticate an arbitrary stream itself.

A guard inspects incoming bytes before the upstream buffered HTTP and frame decoder receives them. HTTP headers are capped at 8192 bytes and require HTTP/1.1 status 101, DERP upgrade, and a Connection upgrade token. Transfer-encoded upgrade responses are rejected. Datagram payloads are capped at 1536 bytes, accommodating the configured WireGuard MTU and discovery messages. Server information is capped at 4136 sealed bytes, health text at 1024 bytes, and unknown frame bodies at 256 bytes. Fixed-size events have exact length checks. This prevents the upstream decoder's larger allocation bounds from becoming Femto's effective bounds.

Each connect, send, or receive operation has an absolute deadline and a 32 KiB read/write budget. Previously buffered bytes can add at most one 1024-byte guard read to a receive operation. Unknown-frame loops consume that budget. Fragmented reads charge actual bytes, so packet segmentation does not multiply the charge. Host TLS enforces the enclosing protocol deadline across its individual I/O calls. The TLS handshake and DERP setup each receive their own configured deadline. Other `DeadlineIo` implementations must enforce the same contract.

The wrapper reuses upstream DERP encryption and event decoding, including automatic ping replies. Protocol or I/O failure drops the client and transport; later operations return a closed-state error. `close` drops them explicitly. Application data received from DERP still requires WireGuard authentication and current data-plane policy before release. Relay metadata and a server's claimed source key do not independently authorize plaintext delivery. Session pooling, peer-map invalidation of pending relay work, rate-limit handling, reconnection, and the concurrent network actor remain unfinished.

A local TLS server fixture decodes client information, emits sealed server information, exchanges datagrams, and checks ping replies. It then sends an oversized header and verifies that the session closes. Additional tests cover fragmented headers, missing upgrade headers, oversized lines, frame bounds, unknown-frame budgets, and refusal to return a session before authenticated server information. A separate public-relay probe exercises a live DERP server. An independent Tailscale client is exercised over direct UDP by the [Headscale check](headscale-qualification.md); independent-peer DERP remains unqualified.

## Public-relay interoperability probe

The opt-in host example creates two ephemeral identities, opens verified TLS/DERP sessions to one relay, exchanges a WireGuard handshake through that relay, and sends an IPv4/UDP request and response through WireGuard and receive policy. The responder checks the cryptographically recovered initiator key before installing its session. The probe uses synthetic local peer/policy maps and no coordinator enrollment. It prints one JSON result, retains no identity files, and closes both relay sessions after verification.

Select a current hostname and numeric address from the [public coordinator relay map](https://controlplane.tailscale.com/derpmap/default). The hostname is used for TLS name verification; the numeric address avoids adding an unbounded DNS lookup to the diagnostic. The following target was valid at the recorded test time and can change:

```sh
nix-shell --run 'cargo run --locked -p femto-microlink --example derp-probe -- derp4f.tailscale.com 185.40.234.219:443'
```

The probe is excluded from automatic network execution in `scripts/check`; that script still compiles and checks the example. Each transport operation has a five-second deadline. A receive phase permits at most eight control events before a required packet. This command contacts a public service and sends synthetic test packets only between its own temporary identities.

The 2026-11-07 run against `derp4f.tailscale.com` at `185.40.234.219:443` passed. [Recorded result](../tests/evidence/derp-probe-2026-11-07.json) includes the observation timestamp and target. The 118 ms elapsed value covers one host diagnostic run and is not a device performance estimate. Evidence establishes public DERP transport interoperability for the tested path, including verified TLS, client/server information, relayed WireGuard handshake messages, and bidirectional encrypted IPv4/UDP packets with policy checks. Both WireGuard endpoints use the pinned Rust implementation. Independent WireGuard/Tailscale peers, authenticated coordinator enrollment, direct discovery, relay fallback/reconnect, and Picco execution remain unverified.

The probe now uses `Handshakes` for both identities. The initiating identity resides in a temporary private `HostStore`; `TimestampClock` reserves an epoch in that store before initiating. The store is removed when the probe exits normally. Two rounds exchange initiation and response through DERP, install the initiator session, and send an IPv4/UDP packet through the receiver-index dispatcher to confirm the responder session. Each round verifies application bytes after receive policy and queued-packet release checks, then exchanges a reverse packet. The second round replaces both sessions through the same owners. Disconnect clears data-plane authorization and owner maintenance removes stale routes.

The [managed-handshake result](../tests/evidence/derp-managed-handshakes-2026-11-07.json) records a passing run of this updated path against the same relay on 2026-11-07. Its 185 ms covers one host observation including temporary identity persistence, two relay connections, and two handshake/packet rounds. The relay address was checked against the public coordinator's DERP map before the run. This establishes integration of the handshake owner, confirmation, receiver-index routing, and packet policy over real DERP transport. The diagnostic still uses synthetic peer authorization and explicit UDP policy. It does not verify enrolled maps, a concurrent network actor, automatic rekey scheduling, or an independently implemented peer.

## Host coordinator transport

`host_control::ControlSession` connects verified host TLS to the pinned Rust coordinator client. The caller supplies a machine private key and a control public key obtained through authenticated bootstrap. The connection performs the `/ts2021` upgrade, Noise IK, EarlyNoise parsing, and HTTP/2 settings exchange. The node-key challenge is exposed for registration. A bounded JSON POST method returns the HTTP status, headers, and body for caller validation. The registration wrapper gates `start_map` on authorization of the same node key. The POST path has not had a live registration test.

The host wrapper imposes a two-MiB read/write budget and an absolute deadline on each upgrade or request operation. TLS handshake and coordinator upgrade have separate deadlines. Request bodies and retained response bodies are capped at 64 KiB. The reused client separately allows 16 KiB upgrade headers, 64 KiB EarlyNoise payloads, and one-MiB HTTP/2 frames. HPACK expansion and total peak allocation are not qualified. These host limits are not Picco memory budgets; HTTP/2 parsing, flow control, and allocation behavior still require audit before device integration. A protocol/I/O error closes the session. Invalid caller input is rejected before sending.

`./scripts/probe-control` builds the opt-in host diagnostic, obtains the public control key through verified HTTPS, and establishes an ephemeral machine connection. It requests no registration or map, prints a JSON result, and closes the connection. The bootstrap key response is limited to 4096 bytes. The script's overall network phase has a 45-second process timeout covering bootstrap, DNS, and probe execution. The Rust transport uses ten-second operation deadlines. The script selects the first resolved IPv4 address; address failover remains unfinished.

The probe passed against `controlplane.tailscale.com` on 2026-11-07. [Recorded result](../tests/evidence/control-probe-2026-11-07.json) establishes verified TLS, successful Noise IK with the HTTPS-authenticated server key, a nonzero EarlyNoise node-key challenge, and HTTP/2 settings exchange. The recorded 46 ms is one host observation. The capability value 142 follows the pinned protocol implementation and does not establish support for every corresponding Tailscale feature. No tailnet enrollment occurred, and no user credentials or persistent identity files were used. This probe does not establish registration, map streaming, authorization-policy compatibility, or device behavior.

## Map-stream authorization lifetime

`map_session::MapSession` exclusively borrows a coordinator for one authenticated HTTP/2 response. Construction clears prior authorization. It requires a successful status-200 header event before accepting data, rejects duplicate status fields and unsupported content encoding, and caps retained header metadata to 64 entries and 16 KiB. Data events must fit the default 16 KiB HTTP/2 frame size. Their contents feed the bounded map decoder, so length headers and JSON maps may span arbitrary data events.

A decoding or map-application error, malformed event order, repeated headers, explicit close, EOF, or guard drop disconnects the coordinator. EOF at a partial map is an error. Even successful EOF revokes authorization and requires full resynchronization. The guard exposes its borrowed coordinator for packet operations while open. Callers must preserve the coordinator's ownership contract and pass queued plaintext through its data-plane release check.

`ControlSession::start_map` accepts a fresh streaming `MapRequest` with keepalives and peers enabled. It rejects session-resumption parameters because resumption is not implemented. The returned `HostMapStream` borrows both the connection and coordinator, preventing concurrent requests on that connection. Each `next` call reads one authenticated HTTP/2 event, samples the clock after the network wait, and applies it through the lifetime guard. Each read has the host connection's byte budget and absolute deadline. The configured timeout must accommodate server keepalive intervals; the host API permits up to 60 seconds. Connection errors, cancellation, EOF, and guard drop close transport and authorization together. Cancellation is checked before network processing and again before applying a buffered event.

Host tests pass synthetic HTTP/2 headers and data through the reused event assembler and the map guard. They exercise every split of a complete map, unsuccessful statuses, compression rejection, duplicate headers, data before headers, oversized data, malformed later updates, truncated EOF, and drop. These tests establish the event-to-authorization lifecycle. They do not establish an enrolled coordinator map stream, HTTP/2 memory bounds, or concurrent direct/relay packet processing. The stream API is synchronous; the network actor and enrollment UI remain unfinished.

## Registration authorization

`ControlSession::register` sends the pinned protocol's registration request over the authenticated connection. Each attempt clears prior registration authorization. A successful result authorizes map requests for exactly the submitted node key. Session close clears that result. This entry point rejects zero node keys and rotation requests; journaled rotation uses the separate `register_rotation` entry point.

`enrollment::Enrollment` accepts at most 16 KiB of registration response JSON after the transport's 64 KiB response cap. HTTP errors, malformed JSON, duplicate known fields, invalid approval URLs, and unsupported Tailnet Lock signatures leave registration unauthorized. A server error takes precedence over authorization. Expiry requires a replacement node key. A nonempty approval URL means pending authorization even when `MachineAuthorized` is true, following the [official registration response contract](https://github.com/tailscale/tailscale/blob/main/tailcfg/tailcfg.go). No URL and a false authorization flag also remain pending.

Approval URLs use `url` 2.5.8 parsing, require HTTPS and a host, and reject credentials, fragments, whitespace, control characters, and values over 2048 bytes. The API exposes the URL explicitly for presentation and does not fetch or open it. Debug formatting redacts it. Errors omit server-provided error text and response bodies. The serialized request buffer is zeroized after use; upstream request strings and intermediate JSON/transport buffers are not guaranteed to be zeroized. Tests cover outcome precedence, key binding, URL constraints, redaction, and revocation on invalid responses. Live registration, follow-up UI, reauthorization, and durable key rotation remain unverified or unfinished.

## Host enrollment command

`tailnet-connect --coordinator-ca ROOT.der` selects one explicit coordinator trust anchor for bootstrap, registration, endpoint publication, and reconnect. `--relay-ca ROOT.der` and `--service-ca ROOT.der` independently select DERP and application HTTPS trust; both require `--udp-bind`. Omitted options retain Mozilla roots. The CLI and simulator share a loader that rejects symbolic links and nonregular files, reads at most 16 KiB plus one overflow byte, and retains certificate-chain and hostname verification. Certificate loading precedes identity access. File opening uses no-follow and nonblocking flags before checking the opened file type.

`--relay-only` requires `--udp-bind` and excludes the bound socket from packet polling, sending, discovery, and STUN. It also omits the bound local endpoint from publication. The command still binds the socket for runtime construction. Relay trust and transport selection apply to both the UDP loop and catalog/progress runtime; application TLS uses its separate connector. These options do not disable certificate verification or change system routes.

`femto tailnet-connect DIRECTORY --endpoint IP:PORT` opens or creates the persistent host identity and sends registration over verified TLS and Noise. The parent directory must exist. The command holds the identity store lock until registration and optional map observation finish. The default TLS hostname is `controlplane.tailscale.com`; `--host` supports another coordinator. The Rust HTTPS bootstrap obtains the public control key. `--control-key mkey:HEX` overrides bootstrap with a caller-authenticated key. Automatic address selection is not yet part of this command.

`--auth-key-file PATH` supplies an auth key. `--followup-file PATH` supplies an approval URL returned by an earlier pending response; these options are mutually exclusive. Each input must be a regular file with no group or other permissions, at most 4096 bytes, and one nonempty token. Symlinks are rejected. Trailing CR/LF is accepted. Follow-up URLs also pass the approval URL validator. Input files remain owned by the caller and are not deleted or rewritten. The command does not accept credentials as argument values or read them from environment variables.

`--rotate-node-key` prepares or resumes a durable replacement against the selected coordinator authority. It persists the candidate before connecting and registers its `NodeKey` with the journal's `OldNodeKey`. A pending approval, rejected registration, or connection failure retains the journal. Retry with the same flag, identity directory, host, and port; an optional `--followup-file` supplies the approval continuation. The explicit file remains caller-supplied; the command does not authenticate its provenance or automatically fetch its URL. Ordinary connection without the rotation flag refuses a pending journal. Rotation never substitutes a new machine identity for the stored machine.

The shared control session checks the journal's coordinator and machine binding and the request's candidate, previous node key, network-lock key, and protocol version before sending it. Successful registration invokes the store's durable completion operation before enabling maps or endpoint publication. A commit failure leaves authorization revoked. Cancellation is checked before and after completion; cancellation after a successful commit leaves the new durable identity available for a later ordinary connection. Once a rotation has completed and its journal is removed, another explicit `--rotate-node-key` starts another rotation. Automatic key-expiry scheduling remains unfinished; Picco exposes a separate explicit renewal action.

Host tests exercise CLI journal reuse across local connection failures, request-binding rejection, approval-context isolation, response outcomes, failed commits, and cancellation around commit. The separate [Headscale check](headscale-qualification.md) verifies preauth registration, expired-key refusal, initial-map authorization, active-stream expiry revocation, and durable renewal against an independent local coordinator. ## Handshake ownership

`handshake::Handshakes` owns pending initiator and responder state for one node key. `Initiations` remains an alias for existing callers. The configured capacity is 1–256 attempts shared by both roles, independent of the installed session limit. A peer can have one outgoing and one incoming pending attempt. Each attempt holds the data plane's authorization permit and expires after five seconds. Maintenance removes expired attempts and permits invalidated by map updates or disconnect. Monotonic clock rollback clears pending work and disconnects the data plane.

Initiation obtains a timestamp through `TimestampClock` and its durable epoch-store contract before emitting a packet. Both handshake roles allocate from the same local receiver-index sequence. Indices increase without reuse during the owner's lifetime, including across `clear`. Index exhaustion is an error. A runtime must retain this owner across reconnects or discard all sessions and index routing before replacing it.

Completion selects an attempt by the response's receiver index. The pinned WireGuard implementation verifies the response before the owner installs a session through the original permit. The data plane rechecks generation, peer authorization, and expiry at installation. Duplicate and late responses have no pending state to complete. A failed cryptographic response consumes the attempt because the reused initiator API consumes its handshake state. A retry needs a new timestamp, ephemeral key, and index. Retry rate limits and scheduling remain runtime work; this API does not automatically retry or queue plaintext.

Incoming initiations pass the pinned responder's cryptographic verification and current peer authorization before a response is returned. The owner retains the newest authenticated timestamp for each accepted peer key and rejects equal or older timestamps. This table holds at most 256 keys, survives pending cleanup, map changes, and clock rollback, and never evicts entries. When full it rejects new peer keys. The table is volatile; rebuilding the owner loses its replay history and requires discarding associated sessions and routing. A long-lived runtime still needs an explicit lifecycle for exhausted replay capacity and device restarts.

The responder retains newly derived keys as unconfirmed state. A valid encrypted transport packet confirms the session before installation. Failed authentication keeps the pending attempt available for a valid confirmation. Installation rechecks the original authorization permit. The first plaintext packet passes the same source, destination, and receive-policy checks as established traffic and retains the queued-delivery generation check. An authenticated packet denied by policy can confirm the session but is not released to the application. An encrypted empty keepalive confirms without delivering plaintext. Revocation or timeout before confirmation discards the unconfirmed keys.

`Handshakes::receive` dispatches a transport packet by its receiver index to responder confirmation or an installed session. The route stores a token unique to that installed session, independent of the map authorization generation. Maintenance checks the token against the current and previous authorized, unexpired sessions in the data plane. A harmless map update can preserve both routes. Replacement retains the former current session for receiving until its original expiry or the next replacement. Peer revocation, expiry, disconnect, or replacement of the whole data plane removes the corresponding routes. Each peer has at most two installed routes and the total is capped at 512. The configured session capacity bounds peers; cryptographic storage retains at most two installed sessions per peer, plus separately bounded pending handshake state. `clear` removes pending handshake work while retaining valid active routes and replay timestamps.

The dispatcher accepts only bounded WireGuard transport frames and returns a peer identity only after successful decryption and receive checks. Unknown indices and malformed packets are rejected. Both UDP and DERP runtime adapters can call this API without providing a peer identity to the data-plane receive operation. Socket addresses and DERP source labels do not authorize plaintext. Returned plaintext remains an opaque pending packet until the application boundary calls the data plane's release check.

Tests exchange real local Rust handshake messages and verify encrypted keepalive decryption after installation. They also cover replay, corrupted responses and confirmations, pending capacity, duplicate peer attempts, revocation, harmless map updates invalidating old permits, timeout, clock rollback, shared indices, and index nonreuse across clearing. A replayed initiation remains rejected after pending state is cleared. Routing tests cover confirmation through the dispatcher, bidirectional established packets, preservation across a harmless map update, unknown indices, session replacement, delayed packets for old indices, and expiry. The network owner connects this handshake dispatcher to direct UDP and DERP runtime adapters, with initiation pacing, renewal scheduling, and control-worker serialization described below.

## Host UDP transport

`host_udp::UdpTransport` binds a numeric host socket in nonblocking mode. Each send and receive performs one socket operation without retries or an internal queue. Receive returns no packet on `WouldBlock`. Sends return `WouldBlock` to the caller for explicit rescheduling. The caller must revalidate authorization before transmitting queued work. Close drops the socket and subsequent operations return `NotConnected`.

Datagrams are limited to 1536 bytes. Receive uses a 1537-byte buffer so an oversized datagram is rejected even if the kernel truncates a larger payload. A rejected datagram is consumed and the next poll can process subsequent traffic. Empty sends, zero destination ports, unspecified destinations, and multicast destinations are rejected. Binding and receiving support the address family supplied by the caller. Endpoint authorization and path selection remain outside this socket adapter.

`Handshakes::handle` provides a common input method for WireGuard initiation, response, and transport datagrams. It returns an authenticated peer with a response to transmit, completed initiator state, or policy-checked pending plaintext. It takes no socket address or DERP source label as an authorization input. Discovery, STUN, and cookie-reply messages are not handled by this method. An event containing a responder packet does not authorize application transmission until encrypted key confirmation succeeds.

A real IPv4 loopback socket test exchanges a complete handshake, responder confirmation, and bidirectional keepalives. It then exercises denied UDP application data, an allowed UDP packet and plaintext release, policy revocation before queued plaintext release, and peer disconnect. A separate socket test checks empty nonblocking reads, oversized input followed by valid input, outgoing size bounds, and closed-socket behavior. These tests use synthetic peer authorization and locally generated Rust peers. They do not establish NAT traversal, endpoint discovery, direct/relay selection, IPv6 underlay behavior, device sockets, or independent-peer interoperability.

The adapter owns no coordinator or handshake state. The future network actor must disconnect the coordinator and maintain the handshake owner when closing a connection, sleeping, or cancelling. Kernel socket-buffer sizing, polling fairness, retries, rate limits, and concurrent coordinator/relay processing remain runtime integration work.

## STUN endpoint observations

`stun::Discovery` tracks at most eight requests with one outstanding request per IPv4 server. Each transaction expires after five seconds. It reuses the pinned protocol implementation's binding request and mapped-address decoding. Transaction identifiers use 96 random bits from pinned `getrandom` 0.2.17, following the [STUN transaction-ID requirement](https://www.rfc-editor.org/rfc/rfc8489.html#section-5). The caller sends requests on the same UDP socket used for peer traffic and selects servers from trusted configuration or a validated relay directory.

Responses must match both the transaction ID and exact server address and port. The wrapper limits packets to 1536 bytes, requires the declared length to match the whole datagram, checks attribute boundaries and padding lengths, rejects duplicate XOR-mapped addresses and unknown required attributes, and verifies an optional final fingerprint with pinned `crc32fast` 1.5.4. The decoder must produce a nonzero-port IPv4 endpoint whose address is not unspecified, loopback, multicast, or broadcast. A malformed or mismatched response does not consume an otherwise valid pending transaction. A successful response consumes it; late and duplicate responses fail. Clock rollback clears pending requests. Explicit clear supports socket replacement and sleep.

An observation contains the server, mapped endpoint, and elapsed request time. It grants no peer authorization and does not automatically alter coordinator endpoints or direct routes. STUN responses from this public-server usage are unauthenticated. General IPv6 mappings, retransmission scheduling, NAT behavior comparison, and integration with discovery ping/pong remain unfinished.

Tests cover source and transaction matching, timeout, replay, backwards time, capacity, trailing bytes, duplicate mapped addresses, fingerprint corruption, and valid responses. The opt-in host probe sends one request through `UdpTransport` and polls for up to five seconds:

```sh
nix-shell --run 'cargo run --locked -p femto-microlink --example stun-probe -- 185.40.234.219:3478'
```

The [2026-11-07 result](../tests/evidence/stun-probe-2026-11-07.json) records a successful observed IPv4 endpoint with a 10 ms round trip. The server was selected from the current public DERP map's `4f` node and advertised STUN port. The result omits the observed public endpoint. This establishes one successful public-server STUN transaction from the host, not endpoint publication, peer hole punching, NAT interoperability across different networks, or Picco behavior. The numeric target is an observation-time value and must be refreshed from the relay map for later runs.

## Authenticated peer discovery

`discovery::Discovery` reuses the pinned protocol's encrypted ping and pong implementation. Outgoing pings require a currently authorized node, a coordinator-provided discovery key, and a target in that node's coordinator endpoint list or current authenticated CallMeMaybe candidates. A discovery key must identify one authorized node; ambiguous keys are rejected. At most 32 transactions can be pending, with one transaction per peer/endpoint pair. Identifiers use 96 cryptographically random bits. Each transaction holds a data-plane authorization permit and expires after five seconds.

Incoming pings are decrypted before replying. The coordinator must associate the authenticated sender discovery key with one authorized node. A nonzero node key in the ping must match that node. Replies echo the transaction identifier and observed source address. Receiving a ping does not validate a direct path or publish a local endpoint. Incoming ping and pong packets are bounded to 1536 bytes. Bounded trailing padding is permitted, and a zero node-key field is treated as absent, matching the [current Tailscale discovery message behavior](https://github.com/tailscale/tailscale/blob/main/disco/disco.go). The reused parser supports message version zero.

A pong validates a path only when its authenticated discovery key, transaction identifier, and UDP source endpoint match a pending request. The reported observed-source address must be usable but is not automatically advertised. Successful transactions are consumed. At most one validated endpoint is retained per peer, with a total limit of 256. Each path expires after 30 seconds. Queries recheck the original authorization permit and current discovery key and endpoint metadata. Any map-generation change invalidates the permit and requires another probe. Revocation, node expiry, removed endpoints, discovery-key changes, disconnect, and backwards time cannot preserve a stale path.

Tests use locally generated identities and synthetic coordinator maps. They exercise encrypted round trips, source mismatch, tampering, replay, path expiry, wrong node-key binding, zero node-key compatibility, unlisted endpoints, revocation, clock rollback, and ambiguous discovery keys. These tests do not establish discovery interoperability with an independent peer or NAT traversal. Authenticated-ping endpoint learning, scheduler runtime integration, response rate limits, RTT ranking, live endpoint-publication qualification, and independent direct/DERP switching validation remain unfinished. The cached discovery path is an endpoint hint; WireGuard still authenticates every transport packet before application delivery.

`call_me_maybe` encodes 1–16 current local interface or STUN endpoints for an authorized peer. The caller must transmit this message over DERP. `receive_call_me_maybe` is a relay-only entry point: the decrypted sender discovery key must map to the same authorized node as the DERP source label supplied by the adapter. UDP discovery dispatch must not call it. This follows the [CallMeMaybe transport contract](https://github.com/tailscale/tailscale/blob/main/disco/disco.go). The entry point limits the encrypted message to 368 bytes before decoding, validates every endpoint, canonicalizes IPv4-mapped IPv6 addresses, and rejects duplicate endpoints. Invalid messages leave prior valid candidate state intact.

Candidate lists are bounded to 256 peers and 16 endpoints per peer. Each list replaces the peer's prior list, holds an authorization permit, and expires after 30 seconds. `candidates` merges the current list with coordinator endpoints, returning at most 32 unique endpoints. Hints can authorize a probe but cannot validate a path. Matching ping/pong remains required. Candidate replacement or expiry removes dependent pending probes and paths unless their endpoint is still listed by the coordinator. Map-generation changes, discovery-key changes, revocation, and disconnect invalidate candidates through the same maintenance checks. Replaying a valid advertisement can refresh candidate lifetime but cannot extend the separate pong-validated path deadline.

CallMeMaybe tests cover relay-source mismatch, encrypted round trips, fresh endpoints absent from the map, the distinction between candidates and validated paths, validation through ping/pong, list replacement, expiry, revocation, oversized lists, duplicates, unusable addresses, and tampering. These are local protocol tests. Live DERP delivery of CallMeMaybe, automatic CallMeMaybe advertisement, and NAT traversal remain unverified or unfinished.

## Probe scheduling and path selection

`Discovery::next_probe` returns at most one encrypted ping and destination per call. Scheduled sends are at least 50 ms apart globally and 500 ms apart per peer. Unvalidated candidates are visited in round-robin order, skipping endpoints with pending transactions. The existing 32-transaction limit and five-second expiry bound pending work. A validated endpoint is refreshed at ten-second intervals after its next scheduled probe. Per-peer scheduling state is limited to 256 peers and removed when authorization disappears. The scheduler does not retain a socket send queue. Direct calls to the lower-level `ping` API bypass this pacing; runtime adapters must use the scheduler for periodic probing.

`Discovery::select` prefers a currently validated direct endpoint. Otherwise it returns the peer's authorized home DERP region only when the current relay directory contains at least one non-STUN-only server in that region. Missing or revoked authority and unusable relay regions produce no route. `failed_endpoint` withdraws validation for a reported failed direct endpoint, allowing the next selection to use DERP without discarding the peer's WireGuard session. Selection is a current-state decision; queued transmissions must reselect and recheck authorization before sending.

Tests cover encrypted probing followed by direct selection, fallback after a reported path failure, missing and STUN-only relay regions, disconnect, global and per-peer pacing, candidate rotation, pending-request suppression, and retries after expiry. The scheduling constants are prototype defaults, not measured Picco battery or network settings. Socket readiness, polling fairness across peers, pending send cancellation, relay connection pooling, automatic failure reports, RTT ranking, and actual direct/DERP switching remain network-actor work.

## Portable network owner

`network::Network<S>` owns the coordinator, discovery state, handshake state, timestamp clock/store, and application packet queues. Its constructor accepts one device identity and a timestamp store for that identity. No mutable coordinator or data-plane reference is exposed. `apply_map` accepts already authenticated map bodies; it is not a substitute for coordinator transport authentication. Map processing, queue invalidation, and protocol-state maintenance occur under one exclusive mutable borrow.

The outgoing queue holds at most 16 datagrams of at most 1536 bytes, each with a five-second deadline and an authorization permit. Encrypted transport packets also hold a token for the installed session that produced them. Expiry, revocation, or session replacement removes stale output. The incoming queue holds at most eight opaque pending packets bounded by the tunnel MTU. `receive_ip` rechecks policy and generation at release. Every applied map conservatively clears both queues, including maps that leave effective policy unchanged. Invalid maps disconnect the owner. Clock rollback also disconnects. `disconnect` clears authorization, discovery paths/candidates, pending handshakes, routes, and both queues while retaining the timestamp owner and handshake replay history.

`initiate`, `send_ip`, `probe`, and `advertise` enqueue bounded work. `send_ip` requires an installed session; it does not retain application plaintext while waiting for a handshake. `advertise` queues CallMeMaybe for DERP even when a direct path exists. `receive` distinguishes WireGuard from encrypted discovery traffic. UDP discovery input can produce a pong or validate a pending probe. Relay discovery input enters the CallMeMaybe path with its source node label. WireGuard input uses the shared authenticated dispatcher; completed initiator state queues a confirmation keepalive. Replies to authenticated UDP handshakes use the observed source, while selected transport traffic uses validated discovery or authorized DERP routing. STUN socket multiplexing remains outside this owner.

`flush_one` rechecks authorization, expiry, session identity, and route state before invoking one caller-supplied send callback under exclusive ownership. The callback must be nonblocking and must not retain work without its own revocation contract. `WouldBlock` returns the datagram to the bounded queue for a later attempt. Other send errors retain work until its deadline; a failed direct send withdraws path validation so selected traffic can use DERP on retry. Packets without a usable route rotate through the queue rather than preventing inspection of all other queued peers. This API performs no socket I/O itself. Periodic `tick` calls are required while idle.

Combined-owner tests use synthetic authenticated-map inputs and in-process transport callbacks. They execute a relay handshake and confirmation, policy-checked application delivery, direct discovery promotion, a simulated direct-send failure followed by relay retry, inbound policy revocation before release, outbound peer revocation before transmission, queue capacity, `WouldBlock`, expiry, and clock rollback. A separate test fills the incoming queue, rejects overflow, and drains the retained packets through policy checks. The earlier UDP loopback and public-DERP probes exercise lower-level adapters; they do not yet exercise this owner through real concurrent transports.

Device concurrent event loops, ingress CPU/rate budgets, application TCP sockets, and automatic rekey scheduling remain unfinished. Host runtime and UDP application adapters are described below. The portable owner supplies the shared state boundary for those adapters; it is not a completed concurrent network runtime.

## Host control worker

`control_worker::ControlledNetwork` moves a registered control connection to a dedicated reader thread. `host_control_worker` remains a host compatibility alias. `start_with` instead creates and registers the connection inside the worker through a caller-supplied setup closure. This permits ESP-TLS streams that cannot cross thread boundaries. The setup closure receives the shared cancellation flag, and a returned session with a different flag is rejected. The requested stack must be between 64 KiB and 2 MiB; no size in this range is a qualified device recommendation. The caller retains the network owner and accesses it through `run`. The worker transfers authenticated map bodies through a queue limited to eight maps, at most 64 KiB per map, and 128 KiB of retained payload in total. The byte budget includes a dequeued map until application finishes. This permits bursts of small incremental updates without increasing the previous payload budget. Failed sends, map application, and queue destruction release their retained-byte accounting. Queue overflow terminates the stream instead of dropping an update. This limit excludes protocol decoding workspace and temporary allocations; total peak memory remains unqualified.

`run` checks stream state, applies queued maps in order with freshly sampled clocks, maintains expiry, and invokes one network operation. A shared mutex serializes map arrival and stream closure with the operation. The callback must remain bounded and nonblocking. A closure detected during a callback takes effect at the next operation boundary. Once closure is recorded, subsequent callbacks are denied and the owner disconnects. Queued maps cannot restore authorization after closure. Invalid maps, poisoned state, cancellation, and producer drop also deny subsequent operations.

`close` requests cancellation and disconnects the owner without waiting. `close_and_wait` waits up to its caller-supplied timeout, joins a completed worker, and retains an unfinished worker on timeout. Drop cancels and joins before releasing network state. A platform operation or setup closure that ignores cancellation can therefore block destruction. Device callers must retain drivers after a timed shutdown failure. Existing TLS polling bounds cancellation checks during reads; synchronous DNS still has no termination deadline. The Picco and concurrent host runtimes invoke the paced reconnect API.

Local tests cover queued-map closure, output revocation, entry and byte overload, byte-budget reclamation, revocation at the end of a small-update burst, invalid maps, serialization with a concurrent closure, explicit cancellation, producer drop, thread-local setup, retention after a timed shutdown failure, and joined destruction. They use synthetic authenticated-map handoff rather than an enrolled control server. The optional host UDP runtime uses this bridge; relay setup and UDP application sockets are described below; device scheduling remains unfinished.

`restart_with` starts a new control lease on the existing network owner. It requires a fresh, unset cancellation flag and the same stack-size bounds as initial setup. It cancels and disconnects the old lease before attempting replacement. An unfinished reader produces `WouldBlock`; no second reader starts, and the caller retains the old worker for shutdown or a later retry. A finished reader is joined. The new lease has its own map queue and closure state, so old queued maps and producer events cannot authorize or close it. The timestamp owner and responder replay history remain in the existing network object. Transport queues, bindings, TCP flows, and authorization are cleared by disconnect. Setup must register again and obtain a new full map. Spawn or setup failure leaves authorization closed. The Picco and concurrent host runtimes drain relay/publication workers before replacement.

External cancellation is checked at the start of every `run` boundary before queued maps or application callbacks. It does not depend on the reader thread reaching its next I/O poll. Tests cover this boundary, old-map/output removal, fresh lease isolation, registration failure, rejected flag reuse, blocked replacement, and successful retry of setup after joining. These are host lifecycle tests; they do not qualify a live coordinator reconnect or physical sleep/wake.

The worker retains `SetupFailed(ErrorKind)` and `StreamFailed(ErrorKind)` stop reasons. `stop_reason` reports the final reason once the worker has finished. Protocol decoding failures map to invalid data; map HTTP 401/403 responses map to permission denied. Underlying transport I/O kinds are preserved, and an authenticated connection closure maps to unexpected EOF. Byte-budget exhaustion is invalid data, distinct from deadline timeout. The retry-candidate predicate accepts normal stream completion and an explicit set of transport failures: timeout, EOF, reset, refusal, broken pipe, disconnected socket, and unreachable host/network. Cancellation, overload, malformed maps, protocol failures, permission failures, unknown errors, and worker panics are terminal for this predicate. Cancellation and existing invalid-map/overload states take precedence over a later worker error, so ambiguous cancellation races conservatively suppress retry. This classification does not authorize traffic. Reconnect still requires completed teardown, fresh registration, and a full map.

`reconnect_with` supplies a nonblocking reconnect pump on the existing control owner. The caller retains one `Reconnect` value across attempts and supplies the current clock, stack size, and a lazy setup factory. Active calls apply queued maps and expiry checks. A finished worker with a retryable stop reason schedules delays of 1, 2, 4, 8, 16, 32, 60, and 60 seconds. The eighth failed attempt exhausts the budget. Thirty continuously observed seconds with an authorized local address reset the attempt count; an active worker without a full map does not reset it. Pacing is deterministic and has no jitter. Deadline overflow or monotonic-clock rollback closes the owner and returns an error.

Replacement requires both a finished control worker and caller-confirmed teardown of old relay/publication workers. The factory runs only when the delay has elapsed and teardown is complete. It creates the setup closure for the new worker, which receives a fresh cancellation flag. Explicit `close` suppresses retries even if a prior stream failure remains the recorded reason. Manual `restart_with` can begin a new lifecycle after explicit closure. No application request is replayed by this API. Host tests exercise real worker creation with injected transient setup failures, all eight delays, exhaustion, delayed teardown, authorization-based reset, terminal map errors, cancellation during backoff, and invalid clocks. Picco integration is described in [device control reconnection](device-network.md#device-control-reconnection). The [Headscale restart probe](headscale-qualification.md) verifies the portable control owner against an independent local coordinator. The host controller and endpoint-publication replacement have local Headscale evidence. Connected-relay replacement and Picco reconnect qualification remain open.

## Host UDP runtime

`host_network::poll_udp` services the nonblocking host socket through `ControlledNetwork::run`. Each call applies pending maps and checks closure before processing at most eight received datagrams and eight outgoing queue flush attempts. Incoming discovery and WireGuard traffic uses the portable owner's authenticated dispatch. Malformed, oversized, unauthorized, and queue-overflow input increments rejection counters without ending the loop. Socket receive failures propagate to the caller. ## Host relay connection worker

`relay_worker::Dialer<T>` allows one background connection job and one completed result at a time. `host_relay_worker::Dialer` retains the Rustls specialization and host connection setup. The host runtime obtains immutable relay plans from queued packets inside `ControlledNetwork::run`. Direct replies, discovery probes, and traffic with a validated direct route do not request relay setup. Plans are deduplicated by region and capped at four. The CLI uses the shared scheduler for missing home and peer regions, alternating priority after failures and skipping endpoints on cooldown.

Setup verifies that the supplied node key matches the plan before spawning. The worker uses Mozilla certificate roots and the relay descriptor's certificate identity or fingerprint. Fixed numeric addresses take precedence and avoid DNS. Otherwise the system resolver supplies at most eight selected addresses from enabled families. This cap applies to retained addresses; it does not bound the resolver's internal allocations. At most two addresses are attempted, each using the existing five-second TLS/DERP transport limits. Server selection currently uses the first non-STUN node in a region; the pool scheduler tries alternate eligible servers after endpoint failure.

Polling validates the plan against current effective authorization, relay-directory identity, endpoint membership, and local authorization. Invalid plans request cancellation, and stale completed connections are discarded before entering the pool. Ordinary polling joins the worker only after `is_finished`; packet polling never waits for DNS, TLS setup, or worker termination. A cancelled job retains the only slot until it exits. Timed shutdown requests cancellation and retains an unfinished worker on timeout. Drop requests cancellation and joins the worker before returning. Platform services must remain alive until shutdown completes. The system resolver has no cancellation or completion deadline, so a stalled lookup can prevent further relay setup for that dialer. TCP connection cancellation can also wait for its configured connection timeout. These limits do not block control updates or UDP polling during ordinary operation. Destruction can block until an uncancellable platform call returns.

A five-second delay follows job completion before another setup starts. Pending jobs and the same delay suppress repeated attempts. Completed setup failures also receive a thirty-second endpoint cooldown, allowing another demanded region to use the worker; [retry fairness](device-network.md#relay-setup-retry-fairness) records matching, bounds, and remaining limitations. Existing connections continue to use the pool's map and delivery-permit checks. The CLI reports relay setup outcomes and counts relay events, rejected peer packets, and connections removed during relay polling. Packet acceptance into a relay queue does not establish transmission or peer delivery.

Local tests cover pending cancellation without replacement threads, stale completion, failure reaping, identity mismatch, shutdown timeout retention, joined destruction, fixed address selection, disabled address families, and relay demand before and after direct-path validation and revocation. ## Host endpoint publication

The host UDP runtime publishes endpoint snapshots after the control map supplies an authorized local IPv4 address. A snapshot contains the concrete IPv4 socket bind address, when available, plus up to eight fresh STUN observations from the same socket. Wildcard and loopback binds are omitted. Local-interface enumeration for wildcard binds, IPv6 endpoints, and port mapping remain unfinished. Duplicate addresses merge, with STUN classification taking precedence. Logs report publication outcomes and observation counts without endpoint values.

A successful registration creates a publisher bound to the same machine identity and registered node key. Each update uses a separate certificate-verified TLS/Noise/HTTP2 connection to the authenticated control host, numeric endpoint, and bootstrap key. The reused streaming HTTP/2 client does not multiplex publication responses with peer-map events. The request uses `Stream=false`, `KeepAlive=false`, and `OmitPeers=true`, following the [Tailscale map request contract](https://github.com/tailscale/tailscale/blob/main/tailcfg/tailcfg.go). Endpoint types are local (1) or STUN (2). Empty snapshots serialize explicit empty endpoint and type arrays to withdraw expired observations. Endpoint hints never authorize peer traffic.

One background job runs at a time. Polling never joins an unfinished job. Changes coalesce while a request runs; the next request uses the latest snapshot. Successful acknowledgments suppress identical subsequent requests. Completion starts a five-second minimum interval before another attempt. Transient failures leave the snapshot unacknowledged for retry. Each connection and request phase has a five-second timeout and the existing control byte budgets; this is not a single five-second total-job deadline. HTTP 401/403 cancels the shared session. Other non-200 responses remain retryable failures. Local authorization withdrawal after initial assignment ends the diagnostic runtime.

The publisher and live map stream share cancellation. Closing the map guard, owner shutdown, or dropping the publisher cancels outstanding publication I/O. Dropping the publisher also cancels the shared control session and joins an in-flight worker; it is owned for the duration of that session. Explicit timed shutdown retains an unfinished worker on timeout. An already delivered request cannot be recalled. Changed observations can therefore remain advertised until a subsequent update succeeds. The portable publisher is also integrated into the [device runtime](device-network.md#device-endpoint-publication). Live coordinator acceptance of updates and withdrawals, independent peer traversal, physical device qualification, and full-runtime reconnect qualification remain unverified or unfinished.

Local tests check wire fields, explicit withdrawals, endpoint validation and deduplication, single-job coalescing, retry pacing, success suppression, authorization rejection, cancellation, and clock rollback. The worker tests inject a sender; they do not establish coordinator TLS/Noise endpoint-update interoperability. Existing control transport probes cover authentication separately without enrolling a node.

The relay pool reports authenticated WireGuard response counts through `PoolStats::handshake_responses`. A DERP packet increments this counter only after `Network::receive` accepts it and its message type is a WireGuard handshake response. Rejected packets retain a separate count. The shared socket poller exposes the relay count as `relay_handshake_responses`, separately from its direct UDP response count. The local TLS/DERP fixture sends a forged response-shaped packet and verifies that it is rejected without increasing the authenticated count. These counters describe accepted responses, not raw frames or connection attempts.

`Handshakes::completed` and `Network::completed_handshakes` report cumulative saturating counts of authenticated session installations for the owner lifetime. Initiator counts advance after response verification and route installation. Responder counts advance only after a valid encrypted transport confirmation and route installation. Pending handshakes, rejected confirmations, replayed packets, and ordinary transport packets do not increment these counters. Disconnect clears active state but retains diagnostic totals. The independent TCP fixture requires two installations and continued traffic beyond the original key lifetime; incoming response counts alone omit peer-initiated renewal.
