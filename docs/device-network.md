# Device application transport

`firmware/picco/src/network.rs` implements the shared catalog HTTP client's `Transport` interface over ESP-IDF LAN sockets. The shared HTTP layer retains redirect limits, origin-scoped credentials, response framing and size limits, OPDS decoding, EPUB streaming, and progress GET/PUT behavior. The reader catalog menu invokes the device adapter through a background worker. Explicit catalog origins can select the tailnet HTTP adapter described below. Selected HTTPS origins use the Mbed TLS callback adapter described below.

The adapter accepts HTTP and HTTPS URLs up to 4096 bytes with hosts up to 253 bytes. It rejects embedded credentials, fragments, unsupported schemes, and port zero. TCP connection attempts use at most eight resolved addresses and at most five seconds per address, capped by the request's limit. The platform resolver remains synchronous and uncancellable. TCP connection establishment can delay cancellation for up to its current connection timeout. Both boundaries recheck cancellation and the limit before exposing a stream.

Connected sockets use nonblocking I/O. HTTPS adopts the connected socket into ESP-TLS and drives the asynchronous handshake entry point as one wait under the request's limit. The raw configuration disables ESP-TLS's internal TCP-connect check because the socket is already connected. This follows the pinned service wrapper's asynchronous adopted-socket path. It avoids reusing the internal select descriptor sets after a connection timeout. The Rust socket owner transfers descriptor ownership to ESP-TLS during teardown so the descriptor is closed once.

HTTPS uses the ESP-IDF full certificate bundle, automatic hostname verification, and certificate validity dates. Compile-time guards reject configurations without the bundle or date checks and reject `ESP_TLS_INSECURE`. There is no insecure fallback, custom trust store, or certificate-verification bypass. HTTPS requires the operational clock readiness checks described below. Certificate verification remains enabled while time is unavailable; requests fail before connecting instead of bypassing date checks.

`femto_catalog::deadline` wraps nonblocking streams with a `Limit` and a shared cancellation flag. A limit is either an instant at which the whole request ends, used by host tools that were given a timeout and by the coordinator connections, or a stall limit: each wait for the other end may last that long, and a request that keeps moving bytes is never ended for its duration. The reader's catalog, progress-sync and update requests use a stall limit of 30 seconds. That is the time a tailnet path that dies needs to be replaced: WireGuard waits 15 seconds for a reply before it starts a new handshake, an attempt takes up to 5 seconds, and a relay connection took up to 8 seconds to make on the reader. Pending operations retry after at most five milliseconds. A terminal error drops the underlying stream. Reads stage at most 1024 bytes and check cancellation and the deadline after the platform operation before copying bytes to the caller. Writes cannot retract bytes already accepted by the platform when cancellation arrives. Higher layers must preserve their existing rules against automatic replay of writes.

The pinned ESP-TLS read wrapper returns zero for both TLS close notifications and transport EOF. The device adapter conservatively treats nonempty reads returning zero as unexpected EOF. Content-Length and chunked HTTP bodies complete through their explicit framing. HTTPS responses that require connection-close framing are rejected, including responses ending with a valid close notification. This restriction prevents acceptance of a truncated close-delimited response through an API that cannot distinguish authenticated shutdown.

The adapter blocks its calling task while servicing a request. `femto_catalog::worker::Worker` runs one feed or acquisition request on a separate thread with a requested 64 KiB stack on ESP-IDF and 2 MiB on the host. New requests return a busy error until the previous task and result are collected. The transport factory runs inside that thread, so transports with thread-local state need not implement `Send`. A completion carries a monotonically increasing request ID. Cancellation and deadline checks before result delivery discard late results, including a feed or staged book that finished before the UI requested cancellation. Dropping a staged result removes its owned temporary file. Stack size and peak parsed-feed memory remain provisional until measured on the Picco.

The screen owner holds the worker before its storage and Wi-Fi fields. Sleep preparation cancels the worker and waits up to five seconds for it to join before changing the frontlight, display, or radio. A timeout retains the task owner and aborts sleep; a later retry can finish shutdown. Dropping the screen joins the worker before releasing other drivers. The worker destructor can block while an uncancellable platform operation runs. It never detaches a task that could retain a socket or storage handle. Host builds with panic unwinding convert a worker panic into an error result; device panic behavior follows the firmware panic policy.

## Catalog menu

An optional `/sdcard/femto/catalog.url` file supplies one UTF-8 HTTP or HTTPS feed URL. The file is limited to 4096 bytes, with surrounding whitespace removed. Embedded credentials, fragments, port zero, control characters, and non-web schemes are rejected. The `.url` extension prevents the library scanner from treating this configuration as a TXT book. Missing or invalid configuration leaves the Catalog menu entry unavailable. Configuration changes require a restart.

Optional `/sdcard/femto/catalog-auth.json` supplies Basic authentication credentials:

```json
{"username":"reader","password":"replace me","allow_http":false}
```

The file must be regular and at most 8192 bytes. Username and password each accept at most 1024 printable ASCII bytes; the username cannot contain a colon. Unknown or duplicate fields, malformed JSON, and unsupported credential characters are rejected without logging their values. Missing credentials enable anonymous access. Invalid or unreadable credentials disable the catalog menu instead of silently falling back to anonymous access. Configuration changes require a restart.

`allow_http` defaults to false. An HTTP catalog requires an explicit true value before credentials can be loaded. Credentials remain scoped to the original `catalog.url` origin, including scheme, host, and effective port. Navigation, redirects, and back requests reuse that scope. A different origin receives no Authorization header; returning to the original origin restores authentication. HTTPS-to-HTTP redirects remain rejected even when `allow_http` is true. HTTP Basic authentication transmits recoverable credentials without transport encryption.

The SD credential file is plaintext; FAT does not provide the host command's Unix private-file permission checks. The owned input buffer, parsed credential strings, and encoded authentication headers use zeroizing owners. Each worker request owns a separate zeroizing header clone. This does not guarantee erasure of parser, HTTP request, operating-system, or TLS temporary copies. Host command credential files retain their existing schema and command-line HTTP opt-in.

Selecting Catalog in the root menu starts a request under the 30-second stall limit. The existing paged touch/button menu shows feed navigation, group navigation, facets, pagination links, search links, Refresh, and publication entries. A publication entry shows its title and authors. Back follows the bounded browser history, returns from publication details, or returns to the root menu. Back while loading discards the pending result and restores the previous feed. Failed loads preserve the previous feed and history. Reopening during an uncancellable operation can report a busy worker until its task exits. The UI never automatically retries a failed request.

Selecting a search link opens the shared on-screen keyboard. It provides lowercase Latin letters, digits, space, grapheme deletion, Clear, and Find through touch or page/select buttons. Catalog and local-library queries use separate buffers. The device editor limits each query to 64 UTF-8 bytes; its visible keyboard does not provide arbitrary Unicode input. Find expands the selected OPDS URI template using the shared `query` keyword implementation and starts an authenticated worker request. Empty queries and unsupported templates remain in the editor with an error. The error replaces the keyboard header until editing resumes.

Search results replace the current feed only after a successful load. Back from results fetches the preceding feed through ordinary browser history. Back from the editor returns to the current feed without a request. Back during a search load restores the previous feed and discards late results. Search uses the same credential origin, deadline, and cancellation rules as feed navigation. Advanced author/title filters and other OPDS search fields remain unsupported.

The catalog panel bounds its labels to 256 non-control characters and its entries to 2048 rows. Ordinary menu rendering displays 32 graphemes per row. Feed limits usually impose a tighter bound. No catalog request starts automatically at boot. Public HTTP feeds can be used on a configured LAN; HTTPS becomes available after clock synchronization. Advanced search fields remain unfinished. Tailnet selection uses the explicit SD origin configuration described below. Existing host commands retain those separately implemented capabilities.

Host tests compile the device menu controller with an injected transport and exercise navigation, publication details, failure retention, cancellation, credential-file loading, credential scope across navigation/back, search expansion and cancellation, and the shared pointer/button event path. Additional tests cover worker capacity, request IDs, blocked-platform cancellation, completed-result cancellation, joined destruction, slot reuse after an unwinding panic, pending-operation retries, partial writes, cancellation before and during I/O, withholding bytes after cancellation, terminal teardown, and deadline expiry. Existing catalog tests cover HTTP parsing and request semantics independently of the platform adapter. The Xtensa build checks the ESP-IDF adapter and its configuration guards. No on-device HTTP/TLS exchange, certificate-failure injection, DNS latency, memory consumption, socket teardown, or power measurement has been performed.

## EPUB acquisition

Publication details expose direct EPUB acquisition links supported by the shared catalog model. A download uses the same stall limit, so its length does not end it, and a 64 MiB body limit. The worker streams into an exclusively created `.femto-download-XXXXXXXX.part` file in `/sdcard/femto`. Authentication and redirects retain the feed client's origin restrictions. The temporary file is flushed, synced, closed, and opened through the reader's EPUB parser. Validation reads metadata and the first chapter; it does not establish that every chapter or image can render.

The UI accepts only the current, uncancelled completion. A book whose content is already on the card is reported as already in the library. The final name is `book-<content SHA-256>.epub`. The pinned ESP-IDF FAT VFS implements rename through FatFs `f_rename`, which refuses an existing destination. Publication therefore preserves an existing book, including a repeated acquisition of identical content. The host controller harness uses no-replacement hard linking for equivalent collision checks. Successful publication starts the existing cooperative library rescan. A rescan failure leaves the saved book in place and reports the error.

Cancellation, validation failure, publication failure, and discarded completions close handles and attempt to remove only the owned temporary file. Cleanup errors can leave a `.part` file. A crash or power loss can also leave one; library scanning ignores that extension. Startup does not delete old staging files. Each creation attempts at most 1024 unused names before reporting a collision limit. The transfer has no resume support. Synchronous validation cannot be interrupted mid-operation; cancellation is checked before and after it, and sleep retains its existing join barrier.

A download leaves the publication view in place under the busy mark and reports progress in its title: whole KiB accepted by the temporary-file writer, including partial writes and excluding failed writes. The view offers no cancel entry; its entries do nothing until the book has arrived, and Back or Back to catalog abandons the download. It changes to Checking book after transfer completion while EPUB validation runs. Progress changes request a screen refresh at most once every two seconds and only while the catalog panel is visible; unchanged values do not refresh. Cancellation and completion discard the per-job counter. Fast downloads or validation can complete before an intermediate label appears. The counter is a staged-byte count, not a percentage, throughput estimate, or durability guarantee. It works with content-length, chunked, and close-delimited transfers because counting occurs after HTTP body decoding. Physical display cost remains unmeasured.

The [2026-11-08 download-progress evidence](../tests/evidence/download-progress-2026-11-08.json) records 11 device-catalog tests, workspace Clippy, and a monochrome Picco build. Tests cover partial-write accounting, throttled titles, validation status, hidden-panel suppression, and cancellation cleanup alongside existing acquisition checks.

File synchronization and no-replacement publication do not establish power-loss atomicity on FAT. Interrupted directory updates can leave missing or duplicate entries. Card removal, storage exhaustion, interrupted publication, and physical download/sleep cycles require device qualification.

The host device-controller tests cover successful authenticated acquisition and rescan, duplicate preservation, malformed EPUB rejection, cancellation, and temporary-file cleanup. Storage tests also cover publication races, failed publication, dropped validated results, and the size boundary. Host fixtures use the 2 MiB host worker stack and do not establish the sufficiency of the 64 KiB device allocation. ZIP directory entries and DEFLATE state use bounded heap allocations described in [dependency decisions](dependencies.md); device peak heap and stack remain unmeasured.

## Device clock

After Wi-Fi obtains an IPv4 lease, the station starts ESP-IDF SNTP in polling mode with immediate clock updates. The first query is sent at once, and while no sample has arrived the query is repeated after 2 seconds, then 4, doubling. The default server is `0.pool.ntp.org`, matching the first server in the pinned service wrapper. An optional `/sdcard/femto/time-server` file overrides it with one ASCII DNS name or IPv4 address. The file is limited to 256 bytes including surrounding whitespace. Hostnames are limited to 253 bytes with labels of at most 63 bytes. Empty labels, schemes, ports, control characters, and IPv6 literals are rejected. Invalid configuration leaves time synchronization unavailable; initialization retries no more than once per minute. A running service reads configuration again only after restart.

The firmware pins an hourly synchronization interval and a randomized initial delay of up to five seconds. These intervals do not bound DNS latency, failed-server retries, or the time until a successful response. The ordinary status row adds `time?` while Wi-Fi is online without a usable clock. Status changes alone do not refresh the e-paper display. Catalog requests fail with a clock-not-synchronized error until a sample is accepted; retry is a user action.

The portable readiness gate accepts samples from 2026-01-01 through the end of 2099. It requires a sample younger than 24 hours and checks that system time agrees with elapsed monotonic time within two seconds. A backwards monotonic reading, implausible date, expired sample, or inconsistent system clock clears readiness until another synchronization callback. HTTPS checks readiness before connection, during the handshake, and around stream I/O. The deadline adapter withholds read bytes if a post-read readiness check fails. Writes already accepted by the platform cannot be retracted.

SNTP provides unauthenticated network time. A forged but plausible synchronization sample can change the clock and pass this operational gate. The implementation does not provide Network Time Security, authenticated time attestation, or persistent rollback protection. Certificate validation uses the resulting platform clock. Authenticated time and independent device qualification remain open requirements where stronger time assurance is needed.

Sleep preparation joins catalog work, stops the time service, clears readiness, and stops Wi-Fi. Driver destruction also stops SNTP before releasing the radio. Wake starts a new service and requires a fresh sample. No clock readiness is restored from SD or retained RTC state. Host tests cover sample bounds, freshness, inconsistent clocks, invalidation, resynchronization, overflow boundaries, and server-name validation. Firmware builds check SNTP linkage. Synchronization after restarts and after timed sleeps (`femto sleep`) has been observed on the Picco. Clock drift, HTTPS certificate failures, and long sleeps remain untested on hardware.

The coordinator worker and UDP poller compile for both targets.

It performs one send or receive operation per call, caps datagrams, detects truncated oversized input with an extra receive byte, and closes explicitly. Host tests cover loopback handshakes, confirmation, revocation, byte limits, nonblocking reads, and closure. The device build checks the standard-library socket API against ESP-IDF.

The device runtime entry point creates a tailnet network owner and opens a UDP socket, when explicitly requested through the reader Tailnet menu. Unused code can be discarded by the linker; image size does not measure an active client's footprint. The portable identity/epoch record owner and the default-partition NVS adapter compile for ESP-IDF; explicit menu provisioning creates an identity only when absent. Application routing and automatic reconnect remain unfinished. ## Durable node-key replacement

`IdentityStore::install_node_key_rotation` and `HostStore::install_node_key_rotation` accept a `NodeKeyRotation` prepared by the pinned protocol identity implementation. The operation checks that the rotation's old public key matches the stored active node key, then replaces only the node key in the existing atomic identity/epoch record. Machine, discovery, network-lock, and backend-log identities remain unchanged. The timestamp epoch is retained; rotation does not permit a timestamp rollback. A stale or already-installed rotation fails without writing.

The new identity becomes accessible through the store only after a successful durable write. Any write error poisons the handle, including a backend error after the record was replaced. Both identity access and timestamp reservations then fail until the store is reopened. Reopening observes the record retained by the backend; the caller must reconcile that key with coordinator state. The main record format remains `FEMTOID1`; journaled rotation uses a separate record.

This storage API does not authorize a rotation, stop existing runtimes, or update the coordinator. Callers must stop all users of the old identity before replacing it. The current runtime and menu do not invoke this API. Expired registration still stops the connection, and ordinary reconnect still uses the persisted key. Installing a replacement without registration coordination is insufficient. Host tests cover successful reopen, identity and epoch continuity, stale rotations, and failed writes; portable backend tests include errors before and after replacement. Physical NVS power-loss behavior and live coordinator rotation remain unverified.

## Pending rotation journal

The portable `rotation::PendingRotation` record contains a candidate identity, the previous node public key, and a hash of the coordinator authority. Hostnames are ASCII-case-normalized; ports remain distinct. Its fixed 265-byte encoding has a version marker and SHA-256 integrity checksum. It accepts only the original active node or the candidate as the current identity, with matching machine, discovery, network-lock, and backend-log identities. The checksum detects corruption; it does not authenticate a record against an attacker with storage access. Candidate identities and serialized secret buffers retain zeroizing ownership.

`HostStore::begin_node_key_rotation(host, port)` saves `rotation.bin` under the existing exclusive store lock before returning the candidate. The journal uses a private temporary file, file synchronization, no-replacement publication, and directory synchronization. Repeated calls and reopen reuse the same candidate for the same authority. A different authority fails without generating or replacing a candidate. Corrupt, oversized, unsafe-permission, or unrelated journals prevent the store from opening. While a journal is pending, ordinary identity access, timestamp operations, and direct unjournaled key installation are blocked.

`HostStore::complete_node_key_rotation` requires an enrollment result permitting the candidate node key. The caller must obtain that result through an authenticated registration with the bound coordinator; the enrollment type itself does not carry endpoint provenance. Completion writes the candidate into the main identity/epoch record before removing and synchronizing the journal. If interruption leaves both records, reopen accepts the matching candidate and requires registration reconciliation again before cleanup. Any ambiguous journal or identity write failure poisons the handle. A journal is not automatically abandoned or replaced, since the coordinator may already have accepted its candidate.

Host tests cover restart reuse, authority mismatch, old-key authorization rejection, pending-traffic blocking, journal corruption, and failure after identity commit but before journal removal. Portable record tests cover every byte's checksum protection, malformed lengths, unrelated identities, and both pre-commit and post-commit identities. The host enrollment command exposes journaled rotation through `--rotate-node-key`. Picco exposes explicit renewal through the separate background job described below.

The portable `IdentityStore` provides the same begin/complete operations and access restrictions. Its backend contract requires journal read, create-only publication, and durable removal under the identity record's exclusive ownership. Reopen validates the journal against the identity record. Provisioning refuses an orphan journal even when no identity record exists. An ambiguous creation, identity replacement, or removal poisons the handle. Reopen accepts either the original or replacement identity with a matching retained journal; a successfully removed journal leaves the replacement identity usable.

The Picco adapter stores the 265-byte journal as `rotation` in the existing `femto_tailnet` NVS namespace. It checks absence before creation, calls `nvs_set_blob` and `nvs_commit`, and compares the readback before returning success. Completion commits and verifies the main identity first, then erases only the `rotation` key, commits, and checks absence. It does not erase the namespace or partition, and it retains the existing refusal to reinitialize corrupt or full NVS. Portable tests inject errors before and after all three mutations. The injected NVS adapter tests cover separate-key storage, restart reuse, epoch continuity, and set/commit/readback failures. The Xtensa build checks the actual NVS API calls. These tests do not establish physical power-loss atomicity or live coordinator reconciliation.

## Coordinator key bootstrap

`firmware/picco/src/control.rs` supplies a coordinator-key bootstrap entry point using the existing verified HTTPS adapter. It accepts a bounded ASCII hostname, nonzero port, protocol version, absolute deadline, and cancellation flag. The exchange requests `/key?v=<version>` with the corresponding Host authority. HTTP redirects are rejected. No HTTP downgrade or unauthenticated key source is supported.

`femto_microlink::bootstrap` shares the bounded HTTP response decoder and key schema with the host connector. It requires status 200, caps headers at 8192 bytes and the decoded body at 4096 bytes, rejects ambiguous framing and unsupported content encoding, and requires a nonzero machine public key. The generic exchange requires its caller to provide an authenticated stream and enforce operation deadlines. The device wrapper checks cancellation and the deadline before connection and after parsing, then checks clock readiness before returning the key. ESP-TLS retains its restriction against connection-close response framing because its read API cannot distinguish authenticated shutdown from truncated transport EOF.

Host tests compile the device wrapper with an injected transport and clock. They verify HTTPS and authority selection, invalid destinations, requests cancelled or expired before connection, cancellation during response reads, unavailable clock at result release, and redirect rejection. Shared decoder tests cover fragmentation, chunked framing, response limits, and invalid keys. The Xtensa build checks the real device connector. No device bootstrap request is triggered at startup; successful physical coordinator interoperability remains unverified.

## Coordinator session transport

`femto_microlink::control_session::ControlSession<S>` accepts a caller-authenticated `DeadlineIo` stream. The host connector delegates to this implementation and retains its endpoint-publication worker. The common session performs the pinned Noise/HTTP2 upgrade, registration, enrollment gating, and bounded streaming peer-map application. Registration remains required before a map request for the same node key. Dropping the map guard closes the connection and disconnects its map target. Serialized registration bodies retain zeroizing ownership.

`control::connect_session` on Picco constructs an HTTPS connection and upgrades it using the bootstrapped coordinator key. The connection implements mutable operation deadlines over the existing nonblocking ESP-TLS adapter. Changing a deadline preserves cancellation and does not reopen a stream closed by an earlier I/O error. Each underlying TLS operation retains certificate/hostname validation and clock-readiness checks. The wrapper checks clock readiness after upgrade before returning a session.

The common session retains the host limits: 64 KiB serialized requests, a 2 MiB wire budget per operation, bounded response bodies, and deadline reset for each map event wait. The upstream HTTP/2 one-MiB frame allowance and HPACK expansion remain unqualified for device memory. The stream contract requires authenticated TLS and cancellation enforcement; the generic Rust type cannot prove those properties for arbitrary third-party adapters.

`ControlSession::register_rotation` accepts a persisted `PendingRotation`, its registration request, and a durable-completion callback. It rejects mismatched coordinator authority, machine identity, candidate or previous node key, network-lock key, and protocol version before I/O. Pending and rejected outcomes never invoke completion. An authorized response remains separate from map authorization until the callback succeeds and a final cancellation check passes. The callback must commit the matching store journal; arbitrary third-party callbacks cannot be proven durable by the session type. Ordinary `register` continues to reject nonzero `OldNodeKey` requests. `device_enrollment::Context::for_rotation` binds approval continuation to the coordinator, machine, candidate, and previous node key and omits auth credentials during follow-up. The host CLI and Picco renewal job use the shared rotation registration path.

Host tests cover existing microlink and catalog behavior, malformed device upgrade responses, and deadline renewal after closure/cancellation. The firmware build instantiates the device entry point against the actual TLS and protocol types. These checks do not establish successful device Noise registration or map streaming. The runtime entry point constructs the enrollment task and network owner, on explicit reader-menu actions; none of these entry points runs automatically at boot.

## Device DERP connection

`firmware/picco/src/relay.rs` connects a selected relay descriptor and numeric address through ESP-TLS, then runs the shared authenticated DERP handshake. `RelayNode::allows_address` now supplies the common host/device check for fixed address overrides, disabled address families, STUN-only nodes, and matching nonzero TLS ports. Unspecified and multicast destinations are rejected. DNS address selection remains the caller's responsibility.

The device TLS connector can dial the selected address while authenticating the descriptor's certificate name. It retains the full certificate bundle and date checks. Device SHA-256 certificate-pin support remains unfinished.

The setup path accepts operation timeouts from one positive duration through 60 seconds, enforces cancellation during TLS I/O, and checks the setup budget and clock before releasing the authenticated session. ## Coordinator worker lifecycle

## Device control reconnection

The Picco runtime calls the portable reconnect pump during its ordinary poll. Retryable control setup/stream failures retain the existing identity, timestamp owner, and bound UDP socket. The runtime closes relay connections and uses zero-timeout joins to drain the relay dialer and endpoint publisher. A replacement control worker starts only after those workers and the previous control reader finish. Each attempt has fresh registration/publication channels. The old channels cannot deliver a publisher into the new control lease. The shared pacing policy bounds attempts and delays; [control-worker behavior](tailscale-data-plane.md#host-control-worker) records the schedule.

Each attempt repeats verified key bootstrap and registration. Once registration has succeeded, subsequent attempts omit the enrollment auth key and approval URL. The immutable setup context retains the original bounded configuration and cloned identity until runtime destruction; its auth string retains the configuration's zeroizing storage. Approval-required, expired, rejected, malformed, and unknown failures remain terminal. Clock readiness failure also stops the runtime. The menu reports transient setup failures as reconnecting and keeps the runtime alive. Explicit Stop and sleep teardown suppress subsequent retries.

Disconnect clears network authorization, application bindings, TCP flows, and transport queues. Existing catalog/download/progress requests are not replayed. A caller can submit a new request after the replacement connection receives a full authorized map. The runtime preserves its monotonic clock origin across attempts. Host tests compile the device runtime with a failing bootstrap adapter, verify one- and two-second retry intervals followed by terminal permission failure, and check that identity/timestamp storage is not reopened or rewritten. Menu tests verify that transient failure retains the runtime and explicit Stop releases it after joining. The portable control owner has separate [Headscale restart evidence](headscale-qualification.md) for successful re-registration, fresh map authorization, and host endpoint-publication replacement. Device TLS re-registration, relay/publication replacement under real I/O, Wi-Fi outages, physical sleep/wake, and memory use remain unqualified. The concurrent host CLI uses a separate [host reconnect controller](tailscale-data-plane.md#host-control-reconnection) around the same portable pump.

## Device startup orchestration

`firmware/picco/src/tailnet.rs` combines an explicitly opened/provisioned NVS store with coordinator setup. Startup validates configuration and clock readiness, clones the identity for worker setup, reserves a durable handshake epoch, and creates a network owner capped at 64 peers and four active sessions. It binds a nonblocking IPv4 UDP socket on an ephemeral port before starting the worker. The owner retains NVS and the timestamp clock on the calling thread. A worker with a provisional 128 KiB stack performs authenticated key bootstrap, Noise upgrade, and registration. These limits require device memory qualification.

`device_config::Config::parse` accepts at most 8192 JSON bytes with this schema:

```json
{"version":1,"host":"controlplane.tailscale.com","port":443,"hostname":"femto-picco"}
```

An optional `auth_key` supplies at most 4096 printable non-whitespace ASCII bytes. Unknown and duplicate fields are rejected. The device hostname is one ASCII label of at most 63 bytes without leading or trailing hyphens. The configuration has no Debug implementation; its owned auth key is zeroized on drop. The upstream registration request makes an additional ordinary String copy whose erasure is not guaranteed. Serialized request bytes retain the shared session's zeroizing owner. The caller must protect and clear any input buffer; no SD configuration file is loaded automatically by this module.

A capacity-one result channel reports authorized, awaiting authorization, expired, or rejected registration, or a generic setup failure. Pending approval URLs are retained in the existing validated/redacted URL type for explicit UI presentation. A non-authorized outcome does not start a map stream. The setup failure path does not overwrite an already reported outcome. Explicit approval follow-up uses the bound continuation described below. Explicit node-key renewal uses a separate background job; ordinary connection does not automatically rotate an expired key.

After authorization, the worker requests a fresh streaming map. `Runtime::poll` applies queued authenticated maps and expiry, polls UDP and relay traffic through the controlled network owner, and reports the assigned IPv4 address. An assigned address does not establish peer connectivity. Loss of clock readiness or a terminal polling error cancels the owner and closes the socket. Explicit shutdown also closes the socket. `close_and_wait` retains a blocked worker on timeout; destruction joins before releasing the identity store. The caller must keep Wi-Fi and time service alive until shutdown succeeds.

Host tests exercise strict configuration bounds and compile the actual runtime with an injected bootstrap failure and in-memory identity backend. They verify failure reporting, denied network access after shutdown, joined teardown, identity continuity, and epoch reservation. The Picco firmware builds with the orchestration code. The reader screen starts and polls this runtime through explicit menu actions. Application sockets and physical/live-tailnet verification remain unfinished.

## Device UDP polling

`socket_network` supplies the common bounded UDP loop. Host callers retain the `host_network` API. Each poll receives at most eight datagrams, schedules a paced discovery probe and STUN request, and makes at most eight queue flush attempts. Oversized and unauthenticated datagrams count as rejected input. Blocked relay packets rotate behind direct output and remain queued until a relay adapter can send them or they expire. Host relay polling uses the same receive/probe helper and retains its existing relay pool.

Device polling runs under the coordinator worker's authorization boundary. It cannot receive or release packets after worker closure or a rejected map update. The runtime owns the socket until shutdown or destruction. The reader screen starts and polls this runtime after an explicit menu action. Catalog and progress transports use the shared runtime. Device endpoint publication uses the registered identity and fresh observations from this socket, as described below.

Shared loopback tests cover receive budgets, oversized input, encrypted handshake confirmation, and revocation. The actual device runtime is compiled into host failure-path tests and into the Xtensa image. ## Nonblocking device relay adapter

`relay_pool` shares the connection, authorization checks, and four-region pool between host and device. `host_derp` retains aliases and the Rustls connector. The `Transport` contract requires bounded nonblocking operations, cancellation checks, preserved TLS buffering, and closure without flushing retained output. `RelaySession` records the authenticated local node key; attaching it to an authorization plan rejects a mismatched key before conversion or packet I/O. The connector remains responsible for verifying the plan's relay endpoint.

`relay_transport` on Picco supplies the ESP-TLS adapter and an authorized-connection constructor. Setup performs the existing verified TLS and authenticated DERP handshake outside the network-owner lock. The caller must insert the result into the pool under that lock, where the current relay plan is checked again. The adapter consumes the blocking deadline wrapper only after its current deadline and cancellation checks pass. It preserves the underlying TLS context and cancellation token. Subsequent frame, queue, and idle deadlines belong to the shared relay connection.

Each adapter call performs one platform operation. Would-block and interrupted operations retain state for another poll. Reads stage at most 1024 bytes and check cancellation and clock readiness before copying them to the caller. Writes check these conditions before and after the platform operation; already transmitted bytes cannot be retracted. Terminal failures drop the TLS context. The existing ambiguous-EOF rejection remains in the underlying ESP-TLS stream.

Host tests compile the actual device adapter with an injected stream and verify pending I/O, cancellation during reads, withheld bytes, and irreversible closure. Deadline-wrapper tests verify lossless stream handoff and rejection of closed, expired, or cancelled streams. Existing host TLS/DERP tests exercise the shared pool's framing, output limits, packet dispatch, and authorization revocation. The Xtensa build checks the real adapter. The runtime entry point supplies background setup, address resolution, and pool ownership and polling. The screen owns the runtime and joins its work before sleep. Physical/live-tailnet qualification remains unfinished. The runtime maintains a home relay independently of outgoing peer traffic; other relay setup follows queued traffic. See [home relay connection and publication](#home-relay-connection-and-publication).

## Runtime relay setup and shutdown

`Runtime::poll` collects completed relay setup and queued relay demand under the coordinator-worker lock. The portable dialer starts at most one background setup for a missing region. Fixed relay addresses avoid DNS; otherwise the worker retains at most eight addresses from enabled families and attempts at most two. Device setup uses a 30-second budget across resolution and connection attempts, checked after synchronous resolution and before each connection. The platform resolver cannot be interrupted, so this budget does not bound time spent inside DNS. The worker requests a provisional 128 KiB stack. A failed or stale setup imposes a five-second delay before the next; a successful one does not. When the home relay turns out to be a server the pool already holds an ordinary connection to, that connection is told it is the home instead of being replaced.

The device stream retains `Send` through its boxed type. Firmware enables `CONFIG_MBEDTLS_THREADING_C` and `CONFIG_MBEDTLS_THREADING_PTHREAD`, with the custom `CONFIG_MBEDTLS_THREADING_ALT` backend disabled; the pinned SDK wrapper supplies `Send` for the owned TLS context when Mbed TLS threading is enabled. No local unsafe thread-transfer implementation is used. A completed connection moves to the polling thread, where pool insertion revalidates its relay plan. Stale plans cancel pending setup and discard completed connections. A blocked cancelled job retains the single setup slot until it exits.

The shared relay-aware poller receives bounded relay events and UDP input, schedules discovery/STUN, and flushes bounded output under the coordinator-worker authorization lock. Pending relay output is revalidated before platform I/O. Ordinary polling never waits for DNS or TLS setup. It uses the same pool and packet loop as the host runtime.

Shutdown cancels both coordinator and relay setup before waiting, closes the UDP socket and active relay pool, and divides one requested wait budget between both workers. A timeout retains unfinished workers. Destruction cancels first and joins both workers through their owners. Wi-Fi and the time service must remain alive until this completes. The screen invokes this barrier before stopping Wi-Fi or time services. Host lifecycle tests cover stale-job retention, failed setup, retry pacing, timeout retention, and joined destruction; device failure-path tests verify that failed coordinator setup cannot start a relay dial. Successful live device relay establishment and application traffic remain unverified.

## Portable TCP application stream

`application_tcp::Stream` provides the blocking Read/Write adapter on host and ESP-IDF. The host module retains compatibility exports and its host network driver. The Picco `Runtime` implements the portable Driver contract: application operations enter the coordinator-worker authorization boundary, and transport progress polls the existing UDP/DERP runtime. Clock-readiness failures cancel the runtime before application access.

`ThreadShared` allows a Send driver to be owned by multiple threads through a mutex. Runtime lock acquisition uses try-lock and returns WouldBlock on contention. Connect, transfer, and plaintext authorization retry contention under the stream's limit and cancellation flag. With a stall limit, each of those operations is one wait, and waiting for the session's first map is not counted at all: the session ends that wait itself, by delivering the map or by failing. A name the map does not offer fails as not found once the stall limit has passed with the map present. A poisoned runtime lock returns ConnectionAborted. Operations release the lock before retry waits; driver callbacks must still return promptly. Stream destruction defers a contended abort in a deduplicated queue capped at four socket handles. Subsequent driver operations drain that queue. The existing single-thread Shared adapter remains available for host callers.

Reads stage at most 1024 bytes and copy them into the caller's buffer only after the post-operation deadline/cancellation check succeeds. A failed read can consume TCP bytes but does not expose them to the caller. The stream then aborts its socket. Bytes already accepted by a write cannot be retracted. TLS adapters must call authorize before exposing their own buffered plaintext.

Host tests exercise an encrypted HTTP exchange from worker threads, reuse of the shared runtime, deferred abort during a nested operation, idempotent cleanup, lock contention through timeout, poisoned locks, and cancellation after a read without exposing bytes. Device runtime tests deny application operations after shutdown. The Xtensa build checks the portable stream and runtime driver. The reader manager and catalog worker share this driver for selected catalog HTTP origins. Device TLS over application TCP is compiled and integrated for the catalog worker. Physical TLS qualification remains unfinished.

## Physical tailnet test

On 2026-11-22 one Picco joined a Tailscale tailnet of nine other devices with the coordinator `controlplane.tailscale.com` and no auth key: it showed the approval link, and after approval in a browser `Connect existing identity` completed registration. Over a direct WireGuard path on the same LAN it browsed an OPDS catalog on a Linux peer running the official client (a 170 KiB feed in about four seconds), downloaded an EPUB of about 1 MiB in 27 seconds, and uploaded a KOReader reading position. Opening the catalog after a restart, including starting the session, took 18 seconds.

The test found four defects that the Headscale fixture does not exercise, all fixed:

- Tailscale's first map response lists peers under `PeersChanged`, not `Peers`. The coordinator rejected that as a delta inside a full map.
- Tailscale sets `MachineAuthorized` on the local node only. Requiring it on peers left every peer unusable, and a request waited out its deadline without sending a packet. An absent flag now permits a peer; an explicit `false` still denies it.
- The eight-packet input queue kept packets that no open flow or bound socket would ever consume, such as late segments of a closed connection. It filled after one large feed and every later connection timed out. A full queue now evicts its oldest unclaimed packet.
- Modem sleep on a weak link (about -74 dBm) lost enough inbound packets to time out the coordinator name lookup. The radio stays awake while a session is open or other network work is in flight.

Release 0.1.3, installed through the on-device update, repeated the catalog test after a restart. Sleeping with a session open closed the session and the radio and entered deep sleep 1.5 seconds after the power press. With a session open, internal memory had about 86 KiB free.

Joining after a restart logs one ESP-IDF task watchdog warning: back-to-back TLS handshakes for the coordinator and relay keep CPU 0 busy for longer than the watchdog period. The warning does not restart the reader, and joining completes.

The relayed (DERP) path was tested with `femto relay`, which makes the reader discard direct datagrams other than STUN so that no direct path forms; the Tailscale client on the server then reported the reader as relayed. The catalog loaded through the relay, and the test led to three changes:

- The home relay was the first region of the directory, New York from a reader in Europe. The reader now sends one STUN request to each region and takes the region that answers fastest as its home. The measurement is settled, with no fixed wait, once every region still silent has been silent for longer than the fastest answer took; when nothing answers, it settles as the requests expire and the first region is used. Round trips are timed to the poll that sees the answer, so regions within some tens of milliseconds of each other are not told apart: the tested reader chose Frankfurt, Paris, London and Helsinki on different starts.
- The reader published its endpoints before its home relay was connected and then again with the home relay. Each publication opens a control connection, and a peer cannot answer through a relay until it knows the reader's home. The first publication now waits for the home relay, unless the directory offers none or its setup has failed. A fixed wait of ten seconds was tried first and was too short: the home relay took eleven seconds to connect.
- The control connection for a publication had five seconds to complete, which it missed while relay handshakes kept the processor busy. It now has fifteen, three times what an unhindered publication took.

After these changes a relayed catalog request after a restart took 15, 26 and 16 seconds including joining, where it had taken 30 seconds or timed out; a direct one still takes 16 to 19 seconds. A relayed 170 KiB feed then still took 21 to 26 seconds against 4 to 5 seconds direct, whichever relay was used. Timing the stages of one poll on the device showed the cause: the reader sent discovery pings to every peer of the tailnet without a confirmed direct path, about ten a second, and sealing one costs a key exchange of about 50 ms on this processor. A poll took 67 ms, so the relay connection, which reads part of one frame per poll, was served twelve times a second. The reader now probes only peers the application has sent to during the session, and after twenty unanswered probes to a peer it probes that peer every five seconds. The relayed feed then took 7 to 15 seconds and the direct one 3 to 8.

Timing one poll again showed three further costs, each now removed:

- Every operation of the network owner begins with a maintenance pass over its tables, and one poll ran that pass 54 times, 8.7 ms of a 16 ms poll. The pass now runs once in a millisecond unless a map changed the authorization in between. An idle poll takes 5 to 6 ms, spread over many small checks.
- The relay connection read at most 1024 bytes in a poll, a third of a full packet. It now reads whole frames, as many in a poll as the UDP socket's datagrams. A relayed 170 KiB feed takes 3 to 5 seconds, the same as a direct one, or 7 seconds as the first transfer after a restart.
- The main loop polled an idle session on every pass, about sixty times a second, a third of one core. It now leaves a session whose last poll moved no packet alone for 100 ms; a request pumps the session from its own thread and is not slowed. By calculation an idle session then costs a twentieth of a core; this was not measured.

Requests then had absolute deadlines: 30 seconds for a feed and 120 for a book, counted from choosing the entry, so the first request after a restart shared its deadline with joining and a long download would have failed while progressing. They now use the stall limit described above. With it a cold catalog open, a warm 170 KiB feed (2 seconds), a book download and an update check all completed on the reader.

A log line timing each connection's lookup, TCP and TLS steps showed where a join's time went. A TLS handshake takes 2.2 to 2.8 seconds on the reader whatever the server, so the time is the reader's own computation. Two connections were avoidable. The relay dialer paused five seconds after every setup, including a successful one, before starting the next; it now pauses only after a failure. And the reader connected to the same relay server twice, first for the peer and then again as its home relay once the latency measurement settled; the first connection is now promoted. A cold catalog open then took 12 seconds where it had taken 17 to 19 the same day: 2.8 seconds for the coordinator key, 2.6 for the control session, 3.4 until the relay was connected, 0.9 until the peer answered and 2 for the feed.

A trace of handshake and discovery packets, logged as `Tailnet packet`, with the chosen route and session state of each peer in use logged as `Tailnet peer`, then showed what the rest of a join waited for:

- The coordinator's key was fetched over its own connection on every join. The key that last opened a session is now kept in internal storage and tried first. If the coordinator answers but that key opens no session, the key is fetched again; a connection that cannot be made is not blamed on the key.
- While a TLS handshake ran, a poll took 250 to 1800 ms and tailnet packets waited. Two key derivations ran on every poll: the relay dialer derived the node's public key before it checked that a setup was already running, and each discovery message agreed a key with its peer and, when sealing, derived the local public key as well, about 50 ms each. The dialer now checks first, and `sealed` keeps the agreed key of the peers last talked to and opens no packet from a sender the map does not name.
- The first WireGuard initiation was answered into the void. A peer answers through a direct path it has verified, else through this node's home relay as the coordinator announces it. The reader measured relay latency afresh on each start and, the measurement being noisy on a busy processor, chose a different home each time (Frankfurt, Paris, London, Helsinki and others), so the peer answered through a relay the reader had left; the host's log showed `derp-18 does not know about peer`. The reader then waited five seconds for the handshake timer. It now keeps the home region of its last session in internal storage and uses it without measuring, choosing another only when that one is gone or cannot be set up. It also initiates again at once when a peer's way to answer appears: when the reader has answered that peer's first ping from an address, and when the home relay connects.
- The first name lookup after idle took one to three seconds or failed, because its first packet met a radio in modem sleep; idle, the reader answered about half of the host's pings within a second. The radio is now kept awake while a menu is open as well as while network work is in flight, and is woken before a request's first packet instead of after the screen update that follows it. A failed lookup is reported as an unreachable host, which the session treats as worth another attempt.

On the tested link, which lost 13 percent of pings with the radio awake that day, a cold catalog open took 8 to 11 seconds after these changes, and a session was established 0.2 to 0.3 seconds after a direct path was found.

A request made before the clock was set, as in the first seconds after waking, failed with `Connect the reader tailnet first`. It now waits: the session manager starts the session when the clock is set, a request looks the session up from its own thread and waits for it under the stall limit, and an HTTPS connection over LAN waits for the clock the same way. A reader without a tailnet configuration still fails at once. The clock itself took up to 45 seconds after a restart, because the time query started after a random delay of up to five seconds and a lost query was repeated only after fifteen. The query now goes out as soon as the link is up and is repeated after two seconds without an answer, then four, doubling. In three restarts the clock was set before a request made 18 seconds after boot, and that request had its catalog 8 to 10 seconds later.

Keeping the clock across sleep, so that nothing waits for the time server, was considered and not built. In five of six restarts the first sample arrived 0.07 to 0.19 seconds after the service started, and in the sixth later than 3.3 seconds. The clock kept through a sleep drifts, and the map session ends itself when the wall clock steps by more than a second, so the correction that follows would cost a rejoin more often than the kept clock saved a wait.

Measured over three timed sleeps with the catalog asked for 7 seconds after waking, the listing was on screen 14.9, 15.8 and 19.2 seconds after waking; in the last the direct Wi-Fi rejoin failed and a scan took its place.

One limit remains. Joining still makes two TLS connections before the first packet (control session and relay) and a third to publish endpoints; the coordinator does not resume TLS sessions, so that cost cannot be avoided by resumption. It was reduced instead. With the ESP-IDF C code built for size, measured in the same session, a handshake took 2.7 seconds to the coordinator and 3.1 to the relay. Building it for speed (`CONFIG_COMPILER_OPTIMIZATION_PERF`) with precomputed base-point multiples (`CONFIG_MBEDTLS_ECP_FIXED_POINT_OPTIM`) gave 1.8 and 2.1 seconds. Software big-number arithmetic in place of the hardware multiplier (`CONFIG_MBEDTLS_HARDWARE_MPI=n`) gave 1.6 to 1.7 and 1.6 to 1.8 seconds over three joins. Two handshakes running at once took 2.2 seconds each. The image grew by 90 KiB. The firmware update check, whose servers present other certificate chains, still passed, with handshakes of 0.9 and 0.4 seconds.

HTTPS to a peer, node-key renewal, a direct path through address translation and a session lasting hours were not tested on the device. While a session that had failed was still open, two firmware pushes over the USB console timed out, both exactly at a chunk boundary: the reader waited for a chunk that the host never sent. The likely cause is a log line from another thread breaking the acknowledgement apart, which was not reproduced. The reader now repeats an acknowledgement every second until its chunk begins to arrive; a push with three acknowledgements deliberately ignored completed.

## Catalog tailnet routing

An optional `/sdcard/femto/catalog-tailnet-origins` file selects tailnet transport for at most sixteen HTTP(S) origins, one per line. The file must be regular, UTF-8, and at most 8192 bytes. Blank lines and surrounding whitespace are ignored. Origins cannot contain credentials, query strings, fragments, or paths other than `/`. The existing origin parser normalizes hostnames and default ports. Missing configuration leaves catalog requests on LAN transport; malformed configuration disables the catalog menu. Configuration is read at startup.

For a catalog at `http://books.example.ts.net:8080/opds`, the route file contains `http://books.example.ts.net:8080`. The URL in `catalog.url` still includes `/opds`. The reader opens a tailnet session with its existing identity when a service routed through the tailnet is used, so the Tailnet menu is needed only to create the identity, approve it, or disconnect. A request made while the session is still starting waits for it; the stall limit starts once the session has its map. Each connection, including a redirect or acquisition connection, selects transport by its exact scheme, hostname, and port. Unlisted origins use LAN. A selected tailnet origin never falls back to LAN after failure.

The device tailnet adapter routes HTTP and HTTPS over encrypted WireGuard/DERP TCP. Peer names resolve only through the authenticated coordinator map; numeric addresses are rejected. HTTPS uses the callback-based Mbed TLS adapter with the same peer name for certificate verification and SNI. There is no HTTPS downgrade. Existing catalog Basic authentication rules still require `allow_http: true` for HTTP credentials, including this transport. LAN HTTPS retains its platform certificate checks.

The catalog transport factory snapshots a weak reference to the selected runtime generation when the reader dispatches a menu event. The worker upgrades it when starting the request and retains that generation until its streams close. Missing or disconnected runtimes fail; a later reader reconnect cannot replace the request's runtime. Idle factories do not retain the old NVS store. Feed navigation, search, and EPUB acquisition use the same factory and routing rules. Existing deadlines, cancellation, credential scope, framing, and file publication rules remain in force.

The manager stops the shared runtime before releasing its handle. Worker handles can retain the closed object until request cleanup, but application access is denied after shutdown. A still-running request can temporarily retain the NVS owner and delay another connect action until its cleanup finishes. Ordinary status polling skips a contended runtime lock. Timed shutdown retains ownership on contention or an unfinished worker; destruction waits for shutdown. Cleanup can access a poisoned mutex solely to close resources, without clearing its poison flag or restoring application access.

Host tests cover route-file bounds and validation, missing factory failure without LAN fallback, propagation to request factories, adapter URL/deadline/cancellation checks before peer resolution, unavailable runtime handling, shared-generation lifetime, and cleanup under contention and poisoning. Shared routing tests cover origin selection across redirects and failure without fallback. Existing encrypted TCP tests exercise the application stream separately. The Picco build checks the actual Send requirements and catalog-worker handoff. ## HTTPS over managed tailnet TCP

`tailnet_tls` uses ESP-IDF's pinned Mbed TLS API with custom read/write callbacks into `application_tcp::Stream`. It does not create an OS socket or bypass the selected tailnet route. The adapter initializes separate SSL, configuration, entropy, and CTR-DRBG contexts. Each C context and the callback state has a stable heap address. SSL is freed before its borrowed configuration, RNG, and callback state; teardown does not send close-notify or perform network I/O. The managed socket then drops and aborts its TCP flow.

Configuration requires certificate verification, attaches the ESP-IDF certificate bundle, and sets the authenticated peer name as the TLS hostname. The firmware retains its certificate-date and operational-clock checks. Session tickets and renegotiation are disabled. The pinned device configuration enables TLS 1.2; TLS 1.3 remains disabled. The adapter checks the certificate verification result after handshake and rechecks authorization before returning the stream. Custom roots, client certificates, and ALPN configuration are not exposed.

The managed socket enforces the request's limit and cancellation during callback I/O. Callbacks also check clock readiness and socket authorization before and after access. Rust unwinding panics are caught before returning through the C boundary; device panic behavior still follows the firmware panic policy. Callback errors retain their I/O error kind and terminate the TLS owner. Mbed TLS pending results retry only after another authorization/deadline check. Native entropy and cryptographic calls cannot be interrupted mid-call; their stack, heap, and wall-time costs need device qualification.

Every TLS operation checks tailnet authorization even when Mbed TLS already holds decrypted plaintext. Reads stage at most 1024 bytes and copy to the caller only after the final checks succeed. Writes submit at most 16 KiB and can return a partial count. Bytes already sent cannot be retracted. Explicit peer close-notify produces cached EOF after authorization checks; a zero read without close-notify is UnexpectedEof. This distinguishes authenticated shutdown from truncation through the direct Mbed TLS API, unlike the ESP-TLS wrapper used for ordinary LAN HTTPS. Any terminal error frees the TLS contexts and rejects later use.

Host tests compile the actual device owner against an injected Mbed TLS ABI. They check required verification, bundle/hostname configuration, context cleanup on setup and verification failures, callback timeout/panic handling, withheld plaintext after authorization loss, clean closure versus truncation, and clock failure. These tests verify ownership and error handling; they do not perform cryptographic certificate verification or a real Mbed TLS handshake. The HTTP adapter tests verify that a refused managed TCP connection never enters TLS setup. The Xtensa build checks signatures and linkage against the actual SDK.

Run `./scripts/check-native-tls` for real TLS handshakes using the same device Rust source, host Mbed TLS 3.6.7 from the pinned Nix source, and a Python/OpenSSL loopback server. The command prints the TLS library versions and creates temporary test certificates. A C bridge provides native context storage and substitutes a local test CA for the ESP certificate bundle. Tests verify application writes, a 22000-byte response, trusted-certificate acceptance, rejection of wrong-hostname, expired, and untrusted certificates, authenticated closure versus truncation, and withheld buffered plaintext after cancellation. The fixture uses TLS 1.2 and an OS TCP socket with deadlines and cancellation.

The Picco SDK uses Mbed TLS 3.6.5. The host fixture does not qualify that build, the ESP certificate bundle or entropy source, TLS over the managed WireGuard/TCP path, target memory/stack limits, or physical certificate-failure cases. Successful device HTTPS over an enrolled tailnet remains unverified.

## Device endpoint publication

The device creates an endpoint publisher after successful registration, using the same machine identity and map request. Runtime polling reads at most eight fresh STUN observations from its existing peer UDP socket under the control worker authorization lock. The wildcard-bound socket also publishes the current Wi-Fi station IPv4 address with its actual bound UDP port. Connection, upgrade, and request phases each use a five-second timeout; this is not one total-job deadline. Already delivered updates cannot be recalled. Sleep does not issue a guaranteed final withdrawal.

## Home relay connection and publication

The device, host UDP diagnostic, and host catalog runtime maintain a home DERP connection independently of outgoing peer traffic. `Network::home_relay_plan` selects the lowest eligible region ID and its first eligible server in coordinator order. Regions marked `NoMeasureNoHome`, STUN-only servers, and servers with both address families disabled are excluded. Selection requires an authorized local node but does not require any peers. This is deterministic initial selection; latency measurements and coordinator region scores do not participate.

The existing single relay worker performs certificate-verified TLS and authenticated DERP setup. A home connection sends `NotePreferred(true)` through the bounded blocking session before conversion to nonblocking polling. The pool rechecks its effective-authorization identity, relay-directory identity, local identity, directory entry, and home eligibility before accepting it. Initial home setup takes priority and can replace an ordinary connection to the same region or evict one ordinary region when the four-region pool is full. Packet permissions remain unchanged. The protocol follows the upstream [DERP preferred-connection frame](https://github.com/tailscale/tailscale/blob/main/derp/derp_client.go) and [home-region exclusions](https://github.com/tailscale/tailscale/blob/main/tailcfg/derpmap.go).

The endpoint snapshot includes `Hostinfo.NetInfo.PreferredDERP` only as a nonzero region after the authorized pool holds the established home connection. An absent connection produces an explicit zero. Serialization preserves the directory's full positive JavaScript-safe integer range rather than narrowing to the pinned protocol type's 16-bit field. Home changes trigger publication even when UDP endpoints remain identical. The existing worker pacing, coalescing, cancellation, identity binding, and shutdown behavior apply. A failure or revocation removes the local advertisement source; the coordinator can retain an earlier value until a successful update. This is not proof of peer reachability or coordinator acceptance.

Tests cover peer-independent selection, exclusions, directory removal, authorization withdrawal, full-width region serialization, withdrawal with unchanged endpoints, pool capacity and same-region replacement. A loopback TLS fixture verifies the preferred flag, relayed WireGuard output, ping/pong, failure removal, and revocation before queued packet transmission. These tests do not establish independent-peer interoperability or physical device behavior.

Connections without stale retained output survive keepalives and updates that preserve effective authorization and the relay directory. Changed authorization or directory contents invalidate old plans, and the next poll schedules replacement under the existing five-second worker pacing. Latency ranking, region-score handling, device certificate pins, and live qualification remain unfinished. Completed setup failures put the exact relay endpoint on a thirty-second cooldown. The scheduler skips that endpoint and can use the worker for another demanded peer region. A blocked resolver or unfinished setup still retains the single worker slot; direct UDP and existing relay connections continue polling.


### Relay setup retry fairness

The shared pool records completed setup failures by local node identity, region ID, and complete server descriptor. A failed endpoint cannot immediately bypass its cooldown through an ordinary peer plan for the same server. Unchanged map updates retain the cooldown. A changed certificate, address, port, hostname, or local identity produces a different retry key. Stale and cancelled worker results do not penalize an endpoint. Successful insertion removes its recorded failure, and pool closure clears retry state.

A failed endpoint becomes eligible thirty seconds after completion. The worker's existing five-second interval between completed attempts remains in effect. Initial missing home setup has priority. After a home failure, the scheduler first considers eligible queued peer regions; after a peer failure or successful insertion, missing home setup has priority again. If all demanded endpoints are cooling down, no setup starts. This avoids immediate retries without creating additional workers. The failure list holds at most 256 descriptors; expired entries are pruned, duplicate failures replace their deadline, and capacity pressure removes the earliest deadline. Target heap usage remains unmeasured.

Host tests exercise a failed home endpoint alongside queued peer regions, suppression of the same endpoint under both roles, retry deadlines, cooldown continuity across map updates, successful insertion, reset on pool closure, and capacity across changing directories. A real worker fixture distinguishes failed from cancelled completion. Polling errors and nonempty health reports also place a still-authorized endpoint on cooldown. Restart frames use the bounded advisory schedule described below. Removal during the pre-poll maintenance checks, including authorization invalidation and idle timeout, does not record an endpoint failure.


### Relay server and home-region failover

When the initial home endpoint is cooling down, selection continues through eligible servers in coordinator order and then through ascending eligible region IDs. Each candidate retains the current effective-authorization identity, relay-directory identity, and local node identity. Home candidates require an enabled address family and exclude STUN-only servers and `NoMeasureNoHome` regions. Selection examines one candidate at a time within the directory's existing 256-server limit; it does not allocate a second complete directory.

For a queued peer destination, selection tries alternate eligible servers within that peer's advertised region. At most eight server plans are retained for one region. It does not redirect peer traffic to an unrelated region. The same endpoint cooldown applies to home and ordinary roles. Peer setup receives a turn after a home failure when an eligible queued destination exists, so scanning alternate home regions does not override the retry-fairness rule.

An established, authorized alternate home remains active when earlier candidates' cooldowns expire. Installing another home connection closes the previous home and preserves ordinary connections, subject to the existing four-region capacity limit. The publisher advertises the established home from the pool, including an alternate region. Unchanged authenticated maps preserve the connection plan. Changes to effective authorization or the relay directory can restart selection; stale retained packet output also forces closure.

Tests cover first-server failure, next-server selection, alternate home regions, exclusion of a peer-only region from home selection, alternate peer servers in that region, retention of a working home after cooldown expiry, and replacement without retaining multiple home connections. The loopback TLS fixture verifies that protocol failure records cooldown while authorization revocation does not. Latency ranking, coordinator score handling, platform-specific capability filtering, and independent-peer qualification remain unfinished. A device-unsupported certificate pin or address family can fail setup and enter cooldown before another candidate is attempted.


### Relay continuity across coordinator updates

Relay plans use the data plane's existing effective-authorization identity and a separate coordinator relay-directory identity. The authorization identity changes when effective peers or policy change, on disconnect, or on invalid updates. The relay-directory identity changes when validated directory contents change or the coordinator disconnects. Explicitly repeating the same directory retains its identity. Server ordering, certificate settings, address settings, and home-selection exclusions participate in directory equality.

Current local authorization, local node identity, endpoint membership, and home eligibility are checked on every plan validation. Removing and restoring a directory does not revive old plans. Revoking and restoring policy does not revive old plans either. An authorization or directory change conservatively invalidates all relay plans, including plans for unaffected servers. Per-server continuity across unrelated directory changes remains unimplemented.

Keepalives, repeated identical maps, and peer endpoint-only patches can preserve an idle relay connection and an unfinished setup job. Queued WireGuard frames retain per-map delivery permits. A map update invalidates those permits even when the connection plan remains valid. If such output is retained, the pool closes the connection before further I/O because TLS buffering or partial frame transmission prevents safely dropping only that packet. The connection-continuity change does not extend packet authority or discovery validation.

Network tests cover unchanged updates, repeated directory contents, endpoint-only patches, directory removal followed by restoration, policy revocation followed by restoration, and disconnect. The loopback TLS fixture inserts a completed connection after a keepalive, preserves it through a repeated full map, and then exchanges traffic on that same connection. Existing fixtures still verify closure before stale queued frames reach the relay. Live coordinator interoperability and physical device qualification remain unverified.


### DERP restart scheduling

An authenticated restart frame closes its connection and withdraws its established-home advertisement. The pool records the endpoint's reconnect delay and preferred retry window from `ReconnectIn` and `TryFor`, following the upstream [restart message semantics](https://github.com/tailscale/tailscale/blob/main/derp/derp_client.go). Femto caps the advisory delay at 60000 milliseconds and the preferred retry window at 30000 milliseconds. Zero delay permits immediate eligibility. Zero retry duration receives a one-millisecond selection window; it does not require a retry loop.

Before the reconnect deadline, the same endpoint is ineligible. During its preferred retry window, the scheduler prioritizes that endpoint over alternatives in its region. A restarting home also defers selecting a different home during this window. Other queued peer regions and established connections remain available. Failed setup within the window uses a five-second endpoint cooldown. After the window expires, ordinary endpoint cooldown and alternate-server selection apply. A successfully inserted connection clears its region's restart record.

The pool retains at most four restart records. A new record replaces the same region; capacity pressure evicts the earliest-ending window. Current relay-plan validation removes revoked records, and pool closure clears all restart state. Deadlines use saturating arithmetic. The single worker and its global five-second completion interval remain unchanged. A busy worker, stalled resolver, short preferred window, or unavailable transport can prevent an attempt within the advisory window; the runtime does not block waiting for it.

Unit tests cover delay boundaries, repeated failed attempts inside a window, alternate-home selection after expiry, unrelated peer progress, zero values, oversized advisories, successful insertion, and revocation. A real loopback TLS fixture delivers the restart frame after packet and ping/pong exchange and verifies that early reconnection is suppressed. Live server restart behavior, device timing, and resource use remain unverified. Server traffic-rate limits are separate and remain unfinished.

## Picco node-key renewal

The Tailnet menu exposes `Renew node key / retry`. It requires the existing runtime and any previous renewal job to have completed shutdown. A dedicated 128 KiB-stack worker opens the existing NVS identity on its own thread, creates or reuses the coordinator-bound journal, and performs authenticated rotation registration. It never provisions a missing identity. The worker does not create a timestamp owner, WireGuard network, map stream, or application sockets while rotation is pending. Durable completion precedes the authorized result. The menu then prompts for `Connect existing identity`, which uses the ordinary startup path with the committed key.

Approval outcomes display the validated URL and retain a continuation bound to the candidate, old key, machine, and coordinator. Selecting renewal again submits that continuation without an auth key. Ordinary connection approval and renewal approval use separate fields. Disconnect clears in-memory continuations and requests cancellation; it does not remove the durable journal. After restart, renewal reuses the persisted candidate and can request authorization again. A different coordinator fails journal validation. Rejected or failed renewal retains the journal for reconciliation. After successful completion, selecting renewal again prepares another rotation.

The manager refuses connection, provisioning, or another renewal while either worker is retained. Cancellation and sleep teardown retain the renewal job until its thread has joined and released NVS. The job uses the existing bootstrap and control transport deadlines and cancellation checks; blocking platform calls still require hardware deadline qualification. A failed job reports a generic status without credentials or server response bodies. Tests compile the actual renewal worker with an injected identity-open failure and verify result delivery and joining. Menu tests cover exclusive operation, completion before reconnect, approval retry, and continuation clearing. Storage and shared registration tests cover candidate recovery and commit gating separately. Successful live renewal and physical NVS, Wi-Fi, cancellation, and sleep behavior remain unverified.

`crates/femto/tests/device_rotation.rs` runs the actual renewal worker against durable host storage and injected coordinator responses. It follows pending approval through a failed identity commit, reopen, and successful retry. The test verifies candidate reuse, coordinator mismatch rejection, credential omission during approval follow-up, retained timestamp epoch, and journal removal after success. A held registration fixture verifies that cancellation retains exclusive store ownership until the worker exits, then leaves its pending candidate recoverable. This test does not execute TLS, Noise, NVS, or an independent coordinator; it establishes the worker's integration with the persistence and approval contracts.
