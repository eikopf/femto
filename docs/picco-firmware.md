# Picco firmware

The `firmware/picco` application targets `xtensa-esp32s3-espidf`. It links the shared reader controller, an embedded DejaVu Serif font, Rustybuzz, and the patched Swash rasterizer. Startup identifies the panel, mounts an available SD card, opens a book or the embedded `device-reader.txt` specimen, and displays its first page. GPIO21 and GPIO9 navigate previous and next pages. Touch taps in the left and right thirds and horizontal swipes also navigate. Center taps and the power button open the reader menu. Physical boot and the embedded specimen have run on a Picco with an SE0400NQW47 panel; [qualification](qualification.md) records the tested scope and remaining failures. Manual save-and-sleep is connected to the menu. Wi-Fi station mode is opt-in; LAN catalog browsing and EPUB acquisition use the device HTTP/TLS adapter. Physical sleep/wake behavior is unverified.

Page buttons use active-low inputs with pull-ups. A separate task with an 8 KiB stack samples inputs and sleeps 10 ms between polls, independently of rendering and display refresh. The portable debouncer requires 30 ms of stable input. While reading, a press turns the page as soon as it is stable and a held button emits one event. Inside menus a short press is reported on release and moves the selection, and a press held for 500 ms means back; pressing both buttons reports nothing. The upper button (GPIO21) turns forward by default and the Settings menu's Swap page-turn buttons entry exchanges the two. In menus the upper button moves the selection up by default, with its own Swap menu buttons entry. Horizontal swipes turn pages while reading and move menus by one page of entries. GPIO2, the power/wake button, selects inside menus and requests sleep while reading; without a writable state journal it opens the menu instead. Before sleeping, the panel shows the book title, author and progress with a full refresh. Frontlight brightness and warmth are stepped sliders: a tap sets the level and selecting a slider steps it up, wrapping to zero. A bounded queue holds eight events. Overflow drops the new event; events older than three seconds are discarded when consumed. Task shutdown signals cancellation and joins the worker. Physical long-press, power-button sleep and sleep-screen behavior have not been observed on the device.

The four-level build shows each frame in two steps on the SE0400NQW47 panel: a fast differential black-and-white refresh in which both gray levels are drawn as ink, then an overlay waveform that moves only the gray pixels. One observer reports smooth text edges without a full-panel flash on the tested device; the base takes about 0.5 s and the overlay about 0.4 s more, during which input waits. Other panels keep the absolute four-level update. A full refresh runs after a configurable number of updates, 20 by default, chosen under Settings, Full refresh; the count includes menu redraws. Residue between full refreshes has not been assessed.

Before opening a book at startup the firmware writes its path to `/sdcard/femto/.opening` and removes the file once the first page is on the panel. A marker found at startup means the previous start never got that far, so that book is skipped once and the library opens with a notice. Interrupting a start by hand has the same effect. Opening the marked book again from the library is not guarded.

### Memory profile

Internal RAM offers about 287 KiB of heap and is the scarce resource; the 8 MiB of external RAM holds fonts, framebuffers, caches and book data. Measured on the tested device with Wi-Fi connected and a book open:

| Stage | Internal free |
| --- | --- |
| Application start, after the 96 KiB main stack and system tasks | 178 KiB |
| Peripherals, input task and Wi-Fi driver started | 91 KiB |
| Book open and reading | 89 KiB |

General allocations of every size, Wi-Fi and lwIP buffers, and mbedTLS allocations are directed to external RAM. Before that, book and reader state held about 60 KiB of internal RAM in small allocations and Wi-Fi left about 50 KiB free. Layout and page-turn times did not change measurably. The main stack is the largest remaining internal user; its measured peak use is about 47 KiB. A task stack in external RAM cannot run flash operations, which ESP-IDF asserts, so moving the reader's stack there would require routing NVS access through an internal-stack task. Worker threads started after the peripherals, such as the 64 KiB catalog and sync worker, take their stacks from external RAM; the largest free internal block could not hold one. NVS access from such a thread runs on a short-lived internal-stack helper thread. TLS and the tailnet client have not been run against this budget.

The FreeRTOS tick is 1 ms. ESP-IDF implements a sleep shorter than one tick as a busy wait, and the network code polls nonblocking sockets with 1 ms and 5 ms sleeps. With the default 10 ms tick a catalog worker waiting for a response spun at its priority, starved the idle task, and stalled responses of about 90 KB until their 30-second deadline. The TCP receive window is 32 KiB so that such a response does not need a radio round trip for every few packets; on the test network a 92 KB feed arrives in one to two and a half seconds.

The main task stack is 96 KiB. Opening an EPUB whose first page holds a JPEG overflowed the earlier 64 KiB stack without a panic message and restarted the device; the JPEG decoder state now lives on the heap, and the measured peak with that fixture and stack is about 48 KiB. Glyph rasterization alone uses about 45 KiB.

The portable `ReaderUi` menu provides a library chooser, contents, chapters, bookmarks, bookmark toggling, links on the current page, return from a navigation jump, and typography settings. Portrait menus use eight rows: a back header, six entries, and a pagination footer. The shared 800x480 landscape layout uses six rows with four entries. Tap an entry to activate it, the header to go back, or either half of the footer to change menu pages. Page buttons move selection; power/select activates it. Both page buttons return from a submenu or close the root menu. The root menu lists Resume reading, Contents, Bookmarks, Library, Catalog, Frontlight, Typography, This book, Settings, Save and sleep and the battery and Wi-Fi status row. This book holds Chapters, Links on this page, Return from jump, Clippings and KOReader sync. Settings holds Firmware update, Network and services, Tailnet, Automatic sleep, Screen orientation, Full refresh, Dictionary, Remote buttons and the two button-swap switches. Back returns to the enclosing menu with the entry it left selected. Empty lists remain escapable. Navigation errors appear in the header and leave the menu open.

Typography controls adjust font size in two-pixel steps, cycle extra stroke weight through 0/0.2/0.4 pixels, cycle coverage exponents through 1/0.85/0.7, and toggle hinting and fractional positioning. These are comparison values, not calibrated Picco defaults. Settings apply to book rendering; menu text uses neutral raster controls. Bookmarks and settings are saved with the current reading position when the menu closes, provided a state journal is available. A power loss while the menu remains open can lose those changes. Menu navigation alone does not write state.

`nix-shell --run 'cargo run --locked -p femto-reader --example device-menu'` writes root and typography previews under `output/device-menu`. Host tests cover shared row hit testing, touch/button navigation, empty lists, bookmark jumps, settings changes, and monochrome menu output. The native desktop simulator uses the same `ReaderUi` menus and row hit testing, with mouse clicks mapped to taps and keys mapped to button operations. Its optional `--library` directory supplies the shared library chooser. X11 smoke tests cover pointer typography controls and book selection; physical Picco touch remains unverified.

The touch adapter uses TMA525C at I2C address `0x24`, SDA7/SCL8 at 400 kHz, reset GPIO10, and active-low IRQ11. I2C operations have a 20 ms timeout. Startup resets the controller and reads its descriptor. If it reports bootloader mode, the adapter requests launch of the installed touch application and then confirms application mode with another descriptor read. It does not program touch firmware. Initialization failure leaves page buttons usable. Three consecutive I/O errors disable touch for the session.

Reports are bounded to 128 bytes and checked for length consistency, duplicate IDs, and coordinate bounds. The portable gesture decoder uses the reference's portrait transform and permits a single active contact. Multi-contact reports, malformed input, identity changes, and stale input cancel the gesture until an empty/lift report releases it. Taps must last 40 to 1000 ms and stay within a 20-pixel movement limit. Horizontal swipes require at least 80 pixels of displacement with at most 60 pixels vertically. A three-second stale timeout cancels without synthesizing a tap. These thresholds and coordinate mapping are provisional. Pinch, long-press, and multi-finger gestures remain unimplemented.

The shared reader handles page boundaries and monochrome rasterization. The firmware maps each page into the panel's native plane and keeps the display handle alive. It tries one reset and full-refresh recovery if an update fails; a second failure stops the reading loop and logs the error. Free heap is logged every ten seconds while the loop runs. The fallback specimen uses bounded in-memory TXT input with the same content hash and paragraph handling as filesystem TXT.

## Reading gestures

Besides taps and horizontal page-turn swipes, the touch decoder reports a vertical swipe (at least 80 px along the view's vertical axis with at most 60 px sideways) and a hold (a contact that has not moved more than 20 px for 600 ms, reported while it is still down; its lift produces nothing). On a reading page each performs a configurable action; menus ignore them.

| Gesture | Default |
| --- | --- |
| Swipe up | Brighter |
| Swipe down | Dimmer |
| Touch and hold | Frontlight controls |

Settings, Gestures lists the three; activating a row selects the next action of nothing, brighter, dimmer, warmer, cooler, frontlight, bookmark and menu. Light steps change the frontlight by one level without redrawing the page. Frontlight controls opened by a gesture return to the page on Back. The assignments are saved with the reading state. Console injection of all three was checked on the tested Picco; recognition of real touches is covered by host tests only.

## Frontlight

The Frontlight menu selects brightness from 0 (off) through 10 and warmth from 0 (cool) through 9 (warm). The driver uses exact discrete entries from the FreeInk Picco table. It does not interpolate percentage brightness. Settings default to off, load at startup, and persist with reading state when menus close. Older state files use the off default.

The input task owns the I2C bus shared by touch at address `0x24` and the frontlight at `0x38`. A bounded four-command channel serializes light changes with touch polling. Failed touch initialization and repeated touch report errors disable touch while retaining the bus for lighting. Each bus transfer has a 20 ms timeout; a light command has a one-second deadline shared by the caller and input worker. The worker rejects a command whose deadline has expired before execution. The result wait uses the time remaining from request creation, including queueing. Expiry does not cancel an I2C sequence already started. Errors appear in the menu and log. Failed changes restore the previous requested settings so the same action can be retried. Every menu activation sends a command, including repeated Off requests. A timeout leaves physical light state unknown. After an I2C error, the driver attempts the last successfully applied setting once, if one exists. It invalidates its configuration assumption before restoration, so restoring a nonzero setting repeats chip setup. Successful restoration still reports the original bus error. If restoration also fails, the error contains both failures, the remembered setting is discarded, and the next valid command requires configuration again. An initial failure has no known setting to restore. This is a bounded register-level recovery attempt; acknowledged writes do not establish physical light output.

Off disables both channels and sets standby. On clears standby, waits 2 ms, configures the chip, writes PWM and current values, and enables the selected channels. Masked register updates preserve unrelated bits. Host tests check table endpoints and bounds, standby transitions, invalid requests, and reconfiguration after injected bus faults. The [frontlight restoration regression](../tests/evidence/frontlight-restore-2026-11-08.json) injects failure at each operation of active-light changes, Off, and activation from a known off state. It checks restored channel registers or standby, preserved unrelated bits, and successful retry. Failures at every operation of the restoration sequence must return both errors without further recovery attempts and require configuration on the next request. The [frontlight command expiry regression](../tests/evidence/frontlight-expiry-2026-11-08.json) runs the firmware command module on the host. It checks expiry at and after the deadline, driver result propagation before expiry, and suppression of a queued command after its caller times out. No physical brightness, warmth, current draw, or interaction with touch has been measured.

## SD card and reading state

The SDMMC adapter uses slot 1, four data lines, 20 MHz operation, and a one-second command timeout. Pins are CLK41, CMD42, D0=40, D1=39, D2=44, D3=43, and card-detect 38. The shared peripheral rail is enabled before card initialization. ESP-IDF mounts an existing FAT16, FAT32, or exFAT filesystem at `/sdcard`, with eight file descriptors and heap-based UTF-8 long filenames. The pinned SDK patch enables exFAT and prevents unused SDMMC slots from resetting GPIO0 during cleanup. GPIO0 controls the shared peripheral rail. No format operation is invoked. Card removal, hot insertion, USB export, and physical SD signal integrity remain unqualified.

Startup loads cached library entries from `/sdcard/femto` and tries the most recently read book on both cold boot and wake. Folder traversal and full-library verification run only through Rescan. The chooser offers all books sorted by title, recent books, and folders containing books. Selecting a book opens its saved source position. The first destination page is paginated and rendered before replacing the current book, so failed opens or first-page rendering errors preserve the current document and position. The chooser retains its error message and remains usable after a failed selection. The shared Search keyboard accepts letters, digits, spaces, deletion, and clear through touch or button selection. It matches titles, authors, and paths.

The boot reading fallback still tries `femto/book.epub`, then `femto/book.txt`, then the embedded specimen. The chooser can open other filenames under `/sdcard/femto`. The Rescan folder action scans again without restarting. The shared cached scanner processes one directory entry or a five-millisecond batch of hash reads per event-loop iteration; Cancel or Back discards the pending result. Successful completion replaces the library and folder lists together. Failures to create a scan retain the previous library. Traversal errors retain accessible books with diagnostics and preserve the previous metadata cache. Book hashing is cooperative; metadata parsing and cache I/O remain synchronous. Incremental directory change detection and card hot insertion remain unfinished. Rescan hashes book contents, so its cost grows with total book bytes; startup does not wait for it. The device scan retains up to 256 books; the host default is 4096. Both stop after 16,384 directory entries and skip traversal deeper than 16 levels. A limit retains the partial library and marks its menu header. At most 64 diagnostic messages of 512 characters are retained. Scan errors opens these messages in paged detail views. Traversal holds up to 17 directory iterators; filesystem handle availability and cancellation latency need device qualification.

Library records retain content ID, path, title, author, and language. They discard chapter and contents trees after inspection. Display metadata is capped at 256 title/author characters and 32 language characters. EPUB parsing, source locators, page navigation, and rendering use the same reader core as the host. Books that exceed the current reader resource limits still fail; these scan bounds do not establish peak parser or device memory use. Switching books temporarily retains both old and new chapter layouts to preserve rollback behavior.

With a mounted card, reading state uses `femto/state0.bin` and `femto/state1.bin`. Each slot contains a version marker, generation, JSON state, and SHA-256 over its header and payload. Startup loads the newest valid slot. If one slot is truncated or fails validation, the other valid slot remains usable. If neither existing slot is valid, saving is disabled and the error is logged. These slots use a separate envelope from the host's JSON state file.

Startup validates each slot in turn and drops its decoded state before inspecting the next slot. Selection retains only generation, slot number, and checksum. It then reads and validates the selected slot again and requires the same generation and checksum before returning its state. This avoids retaining two decoded reader states at once. It adds one file read and JSON decode for the selected slot; startup latency and physical heap peaks remain unmeasured. A changed, missing, or newly invalid winner fails opening without publishing a mixed result. Equal valid generations remain ambiguous. A checksummed slot with invalid settings or an unsupported state version is excluded before generation selection, so it cannot displace an older valid state. The journal still requires one owner; this verification does not provide filesystem locking.

The [journal startup regression](../tests/evidence/journal-startup-2026-11-08.json) checks selection and reload ordering, changed checksum/generation, winner disappearance and read failure, equal valid generations, and recovery from a newer checksummed state with an unsupported version. Existing torn-slot and progress-journal checks exercise the same startup path.

Host JSON saves and journal saves enforce the 4 MiB encoded-state limit while serializing. A bounded writer rejects any JSON write that would exceed the limit, including expansion from escaped bookmark labels. Rejection occurs before creating a host temporary file or opening the next journal slot. It preserves existing saved bytes and does not disable a later valid journal save. Host output remains pretty-printed JSON; journal payloads remain compact JSON. Journal saving hashes the header and payload incrementally and writes the header, generation, payload, and checksum separately, avoiding a second full payload copy. The on-disk frame bytes and generation rules are unchanged. The limit bounds retained encoded bytes, not the already loaded state, allocator overhead, or total device heap use.

The [state encoding regression](../tests/evidence/state-encoding-2026-11-08.json) checks exact JSON byte limits, escaped UTF-8 output, unchanged compact and pretty formats, byte-identical journal frames across slot rotation, and preservation of both slots and the host file after an oversized label is rejected. A subsequent valid save and reopen must succeed. Physical interrupted writes and peak heap use remain unqualified.

After each successfully displayed reading-page change or menu close, the next generation is written to the inactive slot and synced before it becomes active in memory. A failed write disables further saves for that session. The implementation avoids replacement rename, which ESP-IDF FAT does not provide. It assumes one journal owner and does not lock across processes. Checksums detect damaged records; they do not protect against malicious modification or guarantee filesystem metadata survival during power loss. Physical interrupted-write and card-removal tests remain necessary. Until RTC or network time is integrated, the device uses increasing access-order values in `last_opened` to sort recent books; these values are not wall-clock timestamps. Positions and access order still update in memory when saving is unavailable. On startup, the saved orientation selects a 480x800 portrait/inverted viewport or an 800x480 landscape viewport.

## KOReader sync

`/sdcard/femto/kosync.json` enables the shared KOReader sync menu. It supports explicit position upload and download, account verification and account creation over LAN or the enrolled tailnet. [KOReader sync](koreader-sync.md) defines the account configuration, document identity, supported EPUB positions and interoperability checks. Downloaded positions are journaled before the visible page changes. Cancellation or a stale response discards the pending destination. Sleep waits for the sync worker to release its resources. Physical networking, cancellation latency and memory use remain unverified.

## SD fonts

Startup loads optional fonts from `/sdcard/femto/fonts` after mounting storage. The fixed filenames are `regular.ttf`, `bold.ttf`, `italic.ttf`, `bold-italic.ttf`, and `fallback1.ttf` through `fallback8.ttf`. The reader checks them in that order. Files need valid font data supported by both Rustybuzz and Swash; the suffix alone does not establish validity. Only face index zero is loaded from a collection. Missing files are silent. Invalid, unreadable, non-regular, or oversized files produce a serial-log warning and are skipped. A missing or rejected regular face uses embedded DejaVu Serif. A valid regular file avoids allocating the embedded face.

All successfully loaded SD font data share a 4 MiB retained-byte limit. Each read is capped at the remaining allowance plus one byte to detect growth after the metadata check. A failed load does not consume the remaining allowance. The limit excludes the embedded fallback regular face, vector allocation overhead, parser work, shaping data, and raster caches; it is not a peak-heap guarantee. Large CJK fonts may exceed this provisional device limit. Missing style faces use the existing style-selection fallback. Missing character coverage uses the supplied fallback faces in filename order, preserving grapheme boundaries. Font loading adds no synthetic bold or italic effect.

The shared renderer uses these faces for book text and menus. Existing stroke, coverage, hinting, and fractional-position controls still apply. New or changed files are found at the next start; EPUB-embedded fonts and font subsetting remain unfinished. The library scanner ignores the `.ttf` files. Host tests cover absent and malformed files, directory rejection, aggregate limits, lazy default allocation, style-face shaping, Arabic fallback, and raster output. The firmware build checks startup integration. Physical font memory use and text quality remain unqualified.

### Font families

Each subdirectory of `/sdcard/femto/fonts` that holds a `regular.ttf` is a font family named after the directory, with the same optional `bold.ttf`, `italic.ttf` and `bold-italic.ttf`. Typography shows a `Font` row when at least one exists, listing `Default` and up to 24 families with names of at most 32 characters. `Default` is the embedded Libron, or the `regular.ttf` family directly in `fonts` when present. The `fallback1.ttf` to `fallback8.ttf` files directly in `fonts` apply to every family, and the 4 MiB limit applies to one family plus the fallbacks.

Choosing a family loads it, lays the current chapter out again at the same source position and then switches; the page stays readable meanwhile and Back abandons the change. The choice applies to all books and menus and is saved with the reading state. A chosen family that has disappeared from the card falls back to the default. Both families are in memory until the switch completes. On the tested Picco a 760 KB family replaced the default in a few seconds and was restored after a restart.

## Build

From the repository root on x86_64 Linux with Nix:

```sh
./scripts/build-picco
```

The four-level build is the default. The one-bit build remains available:

```sh
FEMTO_PICCO_GRAYSCALE=0 ./scripts/build-picco
```

The firmware embeds the unmodified Libron family (regular, bold, italic, bold italic; see `firmware/picco/fonts`). A `regular.ttf` on the card replaces the whole family with the card's faces.

Its artifacts are written to `output/picco-grayscale` so the monochrome image remains available. The image manifest records `display_levels` as 2 or 4. Grayscale is an experimental comparison path, not a physically calibrated default. Both variants use the same saved typography controls and source positions.

`FEMTO_PICCO_BLUETOOTH=1 ./scripts/build-picco` enables the Bluetooth backend and writes `output/picco-bluetooth`. Combining both options writes `output/picco-grayscale-bluetooth`. Bluetooth uses separate generated SDK configuration and a separate default target directory. An empty `/sdcard/femto/bluetooth-scan` file requests one ten-second scan whose results go to the device log. A `/sdcard/femto/bluetooth-peer` file instead selects one peer for connection attempts, HID service/descriptor discovery, Report Map/Reference validation, notification subscriptions, and reader page turns for its configured address. The [remote-input contract](remote-input.md#picco-discovery) records file formats, bounds, callback ownership, shutdown behavior, and the remaining pairing and physical reconnect qualification. Radio behavior remains physically unqualified.

The script enters `nix/firmware.nix` and builds the separate firmware workspace with its own Cargo lockfile. The compiler recipe is pinned to `aljazerzen/nixpkgs-esp-dev-rust` revision `4209ee705dece664767b2f9da09ede58fc7a59de`, providing Espressif Rust 1.97.0.0. The ESP-IDF package is pinned through `mirrexagon/nixpkgs-esp-dev` revision `5287d6e1ca9e15ebd5113c41b9590c468e1e001b`, providing ESP-IDF 5.5.2. The upstream compiler package currently supports x86_64 Linux. The first build downloads and builds substantial SDK dependencies.

The pinned Xtensa compiler fails during optimized code generation for Serde's primitive `f32` numeric visitor. Layout and text-raster settings therefore deserialize numbers through `f64` and narrow to `f32`. Validation still rejects invalid or out-of-range settings. This permits the normal size-optimized build with thin LTO; reader optimization is not disabled. Host regression tests cover integer and decimal settings and journal round trips.

Outputs are `output/picco/femto-picco.elf`, `femto-picco.bin`, `femto-picco.json`, and `femto-picco.debug.elf`. The release ELF is stripped of symbols and debug information before image generation. The separate unstripped ELF retains symbols for debugging at the same code addresses; byte reproducibility of that debug file is not a packaging requirement. The image's embedded ELF fingerprint refers to the stripped release ELF. The manifest records image size, SHA-256, target chip, display levels, a `bluetooth` boolean, and the reference application slot. The build command supplies the feature metadata; the image parser does not infer it from machine code. Packaging checks the ESP image magic, ESP32-S3 chip identifier, application descriptor, segment bounds, padding, checksum, appended SHA-256, exact image length, and reference slot size. Those checks do not establish hardware compatibility or successful boot.

The SDK enables [ESP-IDF reproducible builds](https://docs.espressif.com/projects/esp-idf/en/v5.5.2/esp32s3/api-guides/reproducible-builds.html), which omits SDK build timestamps and normalizes C source/debug paths. Without fixed namespace paths, Rust-generated debug paths and linker symbol-table ordering differed between clean target directories. Packaging uses the pinned Xtensa `objcopy --strip-all` to remove that non-runtime metadata. The firmware Cargo configuration explicitly sets its workspace directory so an external `CARGO_TARGET_DIR` still loads the Picco SDK defaults. Packaging obtains the actual target directory from Cargo metadata and never substitutes an artifact from the default target directory.

The build script uses the pinned Bubblewrap package to mount the checkout, target directory, and artifact directory at `/tmp/femto-source`, `/tmp/femto-target`, and `/tmp/femto-artifacts` for compilation. This requires Linux user/mount namespaces. The mounts give Cargo stable source paths and crate identities across checkout locations; Rust path remapping alone did not produce identical linked code in the relocation experiment. Rust source locations are remapped to `/femto`. The namespace retains filesystem and network access for the build and is not a security boundary. Source mounts are writable because ESP-IDF generates workspace files. Actual caches and artifacts remain in the selected host directories after the namespace exits. Debuggers may need source-path substitutions for these virtual paths.

`FEMTO_PICCO_OUTPUT` selects an artifact directory, relative to the repository root or absolute.

`./scripts/check-picco-repro` automates relocated clean builds for both display variants with Bluetooth disabled. `./scripts/check-picco-repro --bluetooth` selects Bluetooth explicitly for both variants. The runner clears inherited SDK configuration overrides and records the Bluetooth choice in each build record. It copies the non-ignored repository files into two source directories, creates a separate fresh target directory for each build, uses one Cargo build job, and compares release ELF, image, manifest, and debug ELF. Input hashes are checked after copying and again at completion against both copies and the live tree. The final inventory also detects added and removed source paths. Ignore rules apply to copied sources without Git metadata; non-ignored source file or directory symlinks are rejected. Logs, snapshots, artifacts, and `report.json` remain under a fresh `output/repro-current-*` directory on success or failure. It does not flash hardware or establish reproducibility on a different host.

The [dictionary-enabled comparison](../tests/evidence/repro-dictionaries-2026-11-08.json) passes all four builds with 575 input files unchanged at completion. All compared artifacts are byte-identical within each display variant and also match the corresponding incremental build. The monochrome image is 5,230,608 bytes; the grayscale image is 5,230,704 bytes. The evidence includes a separate completion-time check that the live input path set has not changed. That historical runner checked only the originally recorded files; the current runner also checks the path set.

```sh
CARGO_TARGET_DIR="$PWD/output/clean-target-a" FEMTO_PICCO_OUTPUT=output/clean-a ./scripts/build-picco
CARGO_TARGET_DIR="$PWD/output/clean-target-b" FEMTO_PICCO_OUTPUT=output/clean-b ./scripts/build-picco

cmp output/clean-a/femto-picco.json output/clean-b/femto-picco.json

Release ELF, image, and manifest matched. Comparing images generated from stripped and unstripped ELFs also preserved all loaded segment addresses and bytes except the embedded ELF fingerprint. A subsequent [source-relocation comparison](../tests/evidence/picco-source-relocation-2026-11-08.json) built identical inputs from two checkout paths and separate fresh target directories through the fixed namespace. Release ELF, image, manifest, and debug ELF all matched; the normal incremental build also produced the same release artifacts. The [grayscale comparison](../tests/evidence/picco-grayscale-reproducibility-2026-11-08.json) repeats the relocated clean builds with the `grayscale` feature. Its release ELF, image, manifest, and debug ELF also match. The normal incremental grayscale build produces the same release artifacts and preserves the monochrome output. The four-level image passes structural validation and differs from the monochrome image. Board tests cover four-level packing, all rotations, controller commands, and injected bus failures. These comparisons do not establish reproducibility on another host or physical display quality.

The [current monochrome comparison](../tests/evidence/repro-highlights-2026-11-08.json) repeats relocated clean builds after the selection, highlight, and source-verification changes. Both target directories were absent before building. All 391 recorded inputs match the live tree and both copied sources at completion. Release ELF, application image, manifest, and debug ELF are byte-identical across the two builds. The release artifacts also match the normal incremental monochrome build. The application image is 5,179,616 bytes. Current grayscale evidence follows below. Physical Picco behavior remains unqualified.

The SDK configuration selects 16 MiB DIO flash, octal PSRAM at 80 MHz, a 16 KiB main task stack, and USB Serial/JTAG logging. These settings require physical qualification. Startup enables the shared peripheral rail on GPIO0 and holds the board power latch high on GPIO4. Panel ID reads use half-duplex GPIO transfers before the display pins pass to ESP-IDF hardware SPI at 20 MHz.

## Installation boundary

The build script exports an application image only. It does not invoke flashing or package a replacement bootloader or partition table. `firmware/picco/partitions.csv` records the inspected CrossPoint Picco layout: application offset `0xE0000`, size `0xE70000`, with a separate factory recovery application. It is reference metadata, not evidence of the partition table installed on a particular device.

Hardware installation requires reading the actual partition table, retaining a recovery backup, checking the application slot and device configuration, and establishing a recovery path. Recovery-preserving installation and update tests remain unfinished. The integrated reader image has not been boot-qualified on a physical Picco.

## Device integration

The portable `femto-picco-board` crate identifies YRD0426, DEPG0397, OPM040B3, and SE0400NQW47 from panel replies. Full and fast monochrome updates and absolute four-level grayscale are implemented for all four variants. DEPG0397 uses the reference's custom full waveform; YRD0426 and OPM040B3 use the internal full waveform. All three SSD1677 variants use custom fast waveforms. The SSD2677-based SE0400NQW47 uses a separate initialization sequence, 535-byte custom waveforms, and active-low BUSY. Unknown IDs stop initialization. Grayscale overlay and partial-window updates remain unfinished.

`Display::grayscale` takes native high and low bitplanes, encoded black=00, dark=01, light=10, white=11. SSD1677 complements the planes for the reference's factory-quality waveform and separates refresh activation from power-down. This waveform originates with the X4 and is also used by FreeInk's absolute Picco path; it has not been calibrated for Femto on any Picco variant. SSD2677 powers on before streaming the combined planes, uses its SE0400NQW47 image waveform, and powers down after completion. A subsequent monochrome fast request is promoted to full because grayscale content is not a valid differential baseline. A failed grayscale operation invalidates the ready state until reset.

Four-level rendering retains the existing text quantization and image dithering behavior. Portrait packing rotates both bitplanes without resampling. Grayscale adds one 48,000-byte output plane to the firmware; its SPI adapter still uses a 1 KiB streaming buffer. Host tests decode the rotated pixel levels, check plane inversion and power sequencing, inject failures at every driver bus boundary, and verify cleanup when switching to monochrome. Physical gray separation, text weight, ghosting, and refresh duration remain unverified.

`Display::refresh` accepts `Refresh::Full` or `Refresh::Fast` and returns the mode executed. A fast request after initialization is promoted to full because the glass does not yet match a known previous frame. SSD1677 fast updates leave the previous RAM plane intact until activation completes, then synchronize both planes. The selected fast sequence powers down the controller. SSD2677 fast updates use its retained previous frame and also power down after completion. The firmware requests a full clean after five successful fast page turns. This is a provisional interval; no physical ghosting interval has been qualified.

The SSD1677 path writes both native RAM planes, waits for refresh completion, and restores both planes after activation. The SSD2677 path retains a 48,000-byte previous frame and streams old/new bits as a single 96,000-byte transfer through a 1 KiB buffer. It powers on, refreshes, and powers off before replacing the previous frame. Initialization seeds that frame white, matching the reference's first full refresh. Allocation failure is reported before any display command.

BUSY waits have a ten-second deadline. A transport failure invalidates the driver's ready state until initialization succeeds again. The portrait converter rotates 480x800 black/white pixels into a 48,000-byte native plane without resampling. It rejects grayscale input before changing the destination. The reader renders at two levels for this monochrome path.

Host tests cover known and unknown IDs, waveform selection, RAM synchronization, portrait corners and byte boundaries, and injected failure at every bus operation in initialization and refresh for both controller families. SSD2677 tests decode every transmitted pixel over consecutive frames, check power command ordering, and verify the reset baseline. They cannot establish electrical timing, physical orientation, waveform quality, or power behavior. The FreeInk source and license are recorded in [third-party attribution](../crates/femto-picco/THIRD-PARTY.md).

The inspected board reference also identifies TMA525C touch, four-bit SDMMC, and shared peripheral power rails. Panel detection and waveforms require physical qualification before selecting text raster defaults.

Next work adds grayscale overlay, bounded page production, incremental library indexing, battery filtering, charging-specific sleep policy, and heap and stack measurements. The current diagnostic retains chapter pagination and loads a bounded font set; its compilation does not establish larger-book memory bounds. Host tests navigate the embedded specimen in both directions, check boundary behavior, verify repeatable monochrome output, exercise state-slot corruption and write-failure recovery, test touch cancellation and coordinate mapping, and verify library switching, partial scans, and deleted-file recovery. Typography controls and the physical comparison procedure are recorded in [e-paper typography](typography.md).

## Battery telemetry

The firmware reads calibrated battery voltage on GPIO1 using the pinned ESP-IDF HAL one-shot ADC driver, 12 dB attenuation, and ESP32-S3 curve-fitting calibration. Calibration setup failure leaves voltage unavailable; no uncalibrated fallback is presented as a measurement. After the first conversion, the driver waits 20 ms for startup settling and discards that conversion. Physical probing found elevated initial readings that settled within 20 ms in the observed boot. Three consecutive calibrated samples are reduced to their median, then multiplied by the reference's 2:1 divider ratio. Values outside 2500 to 4500 mV are unknown rather than zero or full. The divider ratio and ADC behavior still require comparison with physical measurements.

The input task samples at startup and every 30 seconds. Startup probes the read-only identity registers for AW32001 at address 0x49 and SGM41562A/B at address 0x03. The tested Picco identifies as AW32001-compatible. Unknown identities leave charger status unavailable. It reads register 0x08 from the identified charger once per sample, on the existing SDA7/SCL8 I2C owner, with a 50 ms transaction timeout. Bit 1 reports external power; bits 4:3 report charge state. Charging requires external power and state 1 or 2, completion requires external power and state 3, and state 0 with external power is reported separately. No charger voltage, current, enable, BATFET, or ship-mode register is modified. If I2C bus initialization fails, charger status is unavailable even if ADC voltage can be sampled. A failed touch-controller initialization does not prevent charger identification.

The portable `battery::Sample` decoder preserves voltage and charger availability independently. Percentage uses the pinned FreeInk Picco charging or discharging voltage curve only when both readings are available. Unlike the reference's discharge-curve fallback, an unread charger leaves percentage unknown. Duplicate top anchors in the charging curve interpolate from 90 to 100 percent. Charge-complete status does not force a low-voltage sample to 100 percent. This remains a voltage-based estimate; no measured capacity, load compensation, temperature correction, presentation smoothing, or sleep-retained filtering is implemented.

One mutex-protected sample replaces the previous sample without growing a queue. Samples older than 60 seconds are unavailable. The main task logs telemetry with its ten-second heap report. On input events it updates a bounded read-only root-menu row containing estimated percentage, voltage, and power state. The row is on the second menu page after frontlight; selecting it changes no settings or reading position. Percentage has a `~` prefix. Updating telemetry alone does not request an e-paper refresh; the next menu render shows the latest sample. Unknown values are displayed explicitly.

Host tests cover all charger status-byte combinations, absent/invalid readings, checked divider arithmetic, median noise rejection, monotonic voltage estimates, duplicate charging anchors, low-voltage charge-complete reports, and the read-only UI row. Firmware compilation verifies the ADC and I2C adapter types. The attached Picco reports external power and charge completion, with approximately 4.33 V after ADC settling. Absolute voltage, percentage accuracy, input latency, and battery drain still require independent physical measurements. Automatic low-battery save/shutdown, charger configuration, and physical sleep/wake qualification remain unfinished.

## Manual sleep and wake

The root menu exposes Save and sleep when startup opened a state journal. A request waits at most five seconds for GPIO2 to remain released for 50 ms, then records the current source position and updates the alternating journal. A missing journal, save error, stuck button, frontlight command error, display sleep error, or Wi-Fi shutdown error aborts preparation. The menu shows the error, attempts to restore saved frontlight levels, and redraws. A failed display sleep invalidates the controller state; the existing present fallback resets it before the redraw. Saved frontlight settings are not changed to zero by sleep preparation.

The panel driver waits for idle before shutdown. SSD1677 restores its initial border setting, disables analog and clock through control2/master activation, waits for idle, then sends deep-sleep mode 2 (`0x10`, data `0x03`). SSD2677 refresh paths already finish powered off; sleep sends its check-code command (`0x07`, data `0xA5`) after idle. Success and every bus failure invalidate differential-refresh state. Initialization is required before any later drawing, and the first fast request after initialization becomes a full refresh.

After successful preparation, the firmware drops the UI and its scanner, reader document, journal owner, and screen resources. This closes book/directory handles, joins the input worker, and releases Wi-Fi, display, ADC/I2C, and SD/FAT drivers before rail changes. FAT unmount uses the pinned HAL's destructor; physical filesystem and card-removal behavior remains unqualified. The last displayed menu remains on the glass; there is no separate sleep artwork.

The final platform path configures active-low ext1 wake on GPIO2, enables its RTC pull-up, disables its pull-down, and retains RTC peripheral power. GPIO4 stays high to retain the board latch. SDMMC pins 41/42/40/39/44/43 and display reset 16 are parked low with holds, then the shared active-low rail on GPIO0 is held high. Unused sleep GPIOs are isolated and deep-sleep holds are enabled before entering ESP-IDF deep sleep. A reported configuration failure restarts the MCU rather than continuing with a partly torn-down reader. This path follows the pinned FreeInk power-manager reference; it has not run on a physical Picco.

Startup releases sleep holds, restores the GPIO4 latch promptly, returns GPIO2 from the RTC domain, and reinitializes peripherals. On an ESP-IDF-reported sleep wake, startup tries the most recently recorded available library book and its saved source position, bypassing the initial library chooser when that succeeds. Missing books or unavailable saved state fall back to ordinary startup. Frontlight settings load from the journal. Wake is a fresh boot, not preservation of the in-memory reader or menu.

Host tests verify shutdown command order for all supported panel variants, faults at each sleep bus boundary, rejection of rendering until reinitialization, and a mandatory full refresh afterward. The UI test verifies that sleep emits one request without changing position or saved settings. Firmware builds verify API linkage and ownership teardown. Physical wake-pin behavior, latch continuity, SD power sequencing, sleep current, RTC-domain power cost, repeated sleep cycles, and state recovery after interrupted sleep entry remain unverified. Automatic low-battery sleep, charging-specific sleep policy, long-press shortcuts, slide-switch handling, physical network-cancellation qualification, and a recoverable installer remain unfinished.

## Inactivity sleep

The device requests automatic sleep after a configured interval without a consumed touch or button event. The Automatic sleep entry under Settings offers Off, 5, 10, 30, and 60 minutes. Ten minutes is the default, including for older state files without an `idle_sleep` field. The timer starts after the initial page is displayed. Library scans and active catalog jobs defer automatic sleep and reset elapsed idle time. Wi-Fi status changes and periodic telemetry do not count as user activity. The timeout applies to reading and menu screens, including while external power is connected. The setting uses the shared reader state and the existing journal save path when returning to reading or preparing sleep. It takes effect immediately and resets elapsed idle time when changed. Unknown serialized choices are rejected. Separate charging behavior remains unfinished.

Automatic sleep requires an available state journal and uses the same preparation, position save, network join, driver teardown, and GPIO2 wake path as Save and sleep. A failed manual or automatic preparation opens the root menu with the error and restores saved frontlight levels. Automatic retries remain suppressed until another user event. This prevents repeated writes or repeated shutdown attempts while an unattended device has a persistent failure. Loss of the state journal disables automatic sleep. The firmware does not discard unsaved state to meet the timeout.

The portable policy uses monotonic milliseconds. A backwards clock sample restarts elapsed idle time. Busy work and disabled sleep reset elapsed time without clearing a failed-attempt suppression. A zero timeout disables the portable policy. Host tests cover the timeout boundary, user activity, busy work, disabled sleep, clock rollback, integer boundaries, configuration changes, and suppression after a failed attempt. Reader tests cover menu selection, legacy defaults, invalid choices, and persistence through host state files and the device journal. Synchronous rendering and book processing delay timer evaluation. Physical idle current, wake behavior, input races during preparation, and automatic sleep during card/network failures remain unqualified.

## Wi-Fi station

Wi-Fi is configured on the device under Settings, Network and services. The Wi-Fi page has an on/off switch, the connection state, the networks found by a scan (strongest first, at most sixteen) and a rescan action. Choosing a secured network opens the keyboard for its password; an open network connects directly. Up to eight networks are remembered, most recently joined first, and a remembered network can be reconnected, given a new password or forgotten. While Wi-Fi is on and no network is joined, the station scans every 30 seconds and joins the strongest remembered network it sees.

At start the station skips that scan and rejoins the access point it was last on, by address and channel, which are kept in NVS under `wifi_last`. The scan takes about three seconds and could not begin until the book had opened; measured on the Picco over 24 restarts, the reader had its address 4.0 to 6.2 seconds after start in 22 and after 10.5 and 12 seconds in two, instead of 10. If that access point does not answer, or the link to it is lost later, the station scans and chooses again. A network with several access points is therefore rejoined through the one last used even when another has become stronger, until that link drops.

The radio is calibrated at every start (`CONFIG_ESP_PHY_CALIBRATION_AND_DATA_STORAGE=n`). With stored calibration data ESP-IDF skips calibration after a wake from deep sleep. In each of five timed sleeps of 15 to 90 seconds the access point then left the first association request unanswered (`Wi-Fi link ended: reason 4`), though it answered after every restart, and the reader had its address about 12 seconds after waking. With calibration it had its address 4.0 to 6.1 seconds after waking in five of six sleeps; in the sixth the request went unanswered at -78 dBm and the scan took over. The energy cost of calibrating at each wake was not measured.

Remembered networks and the on/off state are stored in the internal NVS partition under the `femto_cfg` namespace, not on the SD card. A `wifi.json` found on the card is imported once and then deleted. The partition is not encrypted, because flash encryption is disabled on the Picco: reading the flash over USB reveals the passwords, while removing the card does not. The driver is created when Wi-Fi is first switched on and takes about 40 KiB of internal RAM. The station keeps credentials out of the driver's own NVS storage, requires WPA2 or better for networks with a password, paces reconnection attempts, stops before sleep and starts SNTP once the link is up.

### Service settings

The same panel edits the catalog (address, username, password, plain-HTTP opt-in, tailnet routing), KOReader sync (server, account, plain-HTTP opt-in, tailnet routing) and the tailnet (coordinator, port, device name, auth key). Each service's settings are one JSON document in the `femto_cfg` namespace, in the shape its parser previously read from the card, and every edit is stored at once. A status row reports whether the existing parser accepts the draft. The catalog and KOReader sync read their settings at startup, so the panel offers a restart after a change; the tailnet reads its settings whenever a session starts. `kosync.json`, `tailnet.json`, `catalog.url`, `catalog-auth.json` and `catalog-tailnet-origins` on the card are imported once when nothing is stored for that service, and deleted. Secrets are shown only as set or not set and are entered from an empty field.

Field entry, storage across a restart and the status row have been exercised on the tested device through USB-injected taps. No service has been connected with settings entered this way.

Scanning and the network list have run on the tested device. Joining a network through the on-device keyboard, reconnecting after sleep and behavior at the edge of range have not been observed.

## Orientation transforms

The board crate's `orientation::Orientation` supports portrait, clockwise, inverted, and counterclockwise views. Clockwise and counterclockwise describe turning the physical device from the calibrated portrait position. Portrait and inverted views are 480x800; the landscape views are 800x480. Bounds-checked transforms convert between logical view coordinates and calibrated portrait coordinates. The native panel mapping remains `(portrait_y, 479 - portrait_x)`.

| View | Logical coordinate to portrait coordinate |
| --- | --- |
| Portrait | `(x, y)` |
| Clockwise | `(y, 799 - x)` |
| Inverted | `(479 - x, 799 - y)` |
| Counterclockwise | `(479 - y, x)` |

The orientation packs quantized monochrome pixels or four-level pixels directly into native bitplanes. It requires no resampling, interpolation, or intermediate rotated framebuffer. Invalid dimensions or encodings leave caller-owned planes unchanged. Existing `portrait_plane` and `portrait_grayscale` entry points delegate to the portrait implementation.

The touch decoder applies the same orientation after raw-sensor calibration and before gesture recognition. Taps use logical view coordinates, and horizontal swipe thresholds use the current view's axes. Changing orientation discards the active contact and suppresses gestures until a lift/empty report. Setting the existing orientation preserves the contact.

Host tests exhaustively cover pixel bijection, inverse coordinates, monochrome bits and grayscale planes in each orientation, output preservation on invalid input, rotated taps/swipes, and contact cancellation on orientation change. Existing portrait packing and bus tests remain passing. The device selects the saved orientation and coordinates changes with the input task. Physical rotation qualification remains unfinished.


## Landscape menu geometry

The shared menu renderer and pointer handler use one geometry implementation. Row count is the viewport height divided by 80, capped at eight. The header and footer occupy one row each; the remaining rows contain entries. The 800x480 view therefore displays four entries per page. The renderer reduces cell padding in short rows while retaining the existing 18-pixel font size. Existing 480x800 portrait spacing is unchanged.

The keyboard lays out its 36 letters and digits across the available body rows. It uses six columns in portrait and nine in the Picco landscape view, followed by a footer containing Delete, Space, Clear, and Find. Layouts whose final body row has unused cells ignore taps in those cells. Button selection retains the same character and action order.

Menu width must be between 480 and 2048 pixels and height between 320 and 2048 pixels. Keyboard columns additionally require at least 80 pixels each. Rendering partitions the complete width and height using integer cell boundaries, and pointer lookup uses those same boundaries. Uneven viewport dimensions therefore retain working rightmost and bottommost pixels without gaps between rows or keys.

Host tests cover every rendered row/key boundary, landscape catalog pagination, all footer actions, keyboard letters and digits, empty keyboard cells, uneven viewport dimensions, and portrait regressions. The simulator smoke test covers the existing portrait window workflow. The device orientation menu uses this geometry; no physical landscape test is claimed.


## Device orientation selection

Screen orientation under Settings offers Portrait, Clockwise, Upside down, and Counterclockwise. The device starts cancellable page-by-page reflow before replacing the layout and saved orientation. The current orientation remains active during indexing. Cancel or Back retains the previous view. Completion switches layout and orientation together before the input/display transition. The source position is retained across reflow. Portrait and inverted views use 480x800; landscape views use 800x480. The framebuffer is packed through the selected lossless transform for both monochrome and grayscale output. Physical page buttons retain their previous/next functions in every orientation.

The device renders the new view before beginning the input/display transition. It then sends an acknowledged pause command to the input task, forces a full display refresh, and sends an acknowledged resume command. Each command advances an input generation. Every queued event carries its producer generation; the UI rejects events from earlier generations. While paused, the producer emits no input events. Touch recognition is cancelled at both boundaries, so a contact must lift before it can generate a gesture in the new view. Page/select buttons must all be released before button events resume. Raw touch polling continues while paused, and orientation is applied before gesture recognition.

Input commands share the bounded input-task command channel with frontlight updates. Each orientation command has a one-second acknowledgement timeout. An unavailable command, unknown acknowledgement outcome, or display failure stops the reader instead of continuing with uncertain display/input coordinates. Input generations do not wrap. Startup uses the same pause/full-refresh/resume sequence, including for legacy state that defaults to portrait.

After a successful orientation display, the reader records its source position and saves the setting through the existing state journal, even while the menu remains open. A save failure retains the running orientation, reports the failure in the menu, and disables further saves and sleep until recovery. Restart then uses the most recent recoverable journal slot. The shared state format defaults absent orientation to portrait and rejects unknown enum values. The simulator reads saved layout dimensions but does not expose the hardware orientation menu or rotate its native window.

Host tests cover all four controller reflows, source-position preservation, menu selection, legacy-state loading, journal round trips, input-generation barriers, pause suppression, and button-release gating. Earlier exhaustive bitplane/touch and landscape geometry tests remain applicable. The Xtensa build verifies the actual input-thread command and display wiring; host tests do not execute ESP-IDF GPIO/I2C or establish physical refresh timing. Panel orientation, touch alignment, held-contact transitions, hardware button behavior, grayscale quality, and persistence under power loss still require device qualification.

## Chapter page memory

The shared reader uses `PageCache` for Picco, terminal, and simulator navigation. Initial chapter opening or reflow streams positioned pages into a compact index of start/end source locations. The index retains at most 16,384 entries. Only the selected page retains text lines, positioned glyphs, and image placements. A page turn reconstructs the destination from its indexed start using the retained parsed chapter. Reconstruction checks both page boundaries before replacing the selected page. Font and layout settings must remain unchanged for the index lifetime; reflow builds a replacement index.

The working set includes parsed chapter text, paragraph bidi and hyphenation data, the retained page, the page under construction, and a candidate line or image used to detect overflow. The per-page glyph limit is 131,072. The eager pagination API used for exports and menu rendering retains the earlier 256-page and 131,072-total-glyph limits. Library selections, UI font-size changes, device rotation, and cross-chapter contents/chapter/bookmark/link/preview-follow/back/page-turn navigation use cooperative indexing with cancellation. Synchronous controller actions can still index synchronously. Startup uses cooperative indexing as described below. Sync preparation captures a snapshot without loading chapters; its worker validates source locations before HTTP access, and final reader commit still contains synchronous work. A page turn reanalyzes its source paragraph; large-paragraph CPU and allocation budgets remain unqualified. Persistent page indexes and measured Picco peak memory remain unfinished.

Host tests compare every glyph position, line, image placement, and source boundary against eager pagination across EPUB fixtures. They navigate and reopen a chapter beyond 256 pages, reject invalid page selections without replacing the current page, and verify that a stopped stream does not inspect later invalid content. These tests establish layout equivalence and navigation behavior, not physical memory or latency measurements.

## Cached startup library

Startup loads bounded cached metadata without directory traversal or book hashing. The most recently read cached entry is the first opening candidate on cold boot and wake. Missing or invalid caches leave default-book reading and the Rescan action available. Successful first opening records the selected book in the cache. Rescan discovers other books and performs full-content verification. Cache and state loading remain synchronous.

## Cooperative startup opening

After font, state, and cache loading, Picco builds a bounded candidate list. Cold boot and wake try the most recent cached book first, followed by the default EPUB and TXT paths without duplicates. Each candidate uses the shared cached `ReaderStartup` job. A matching file stamp skips hashing; a miss uses five-millisecond batches of 8192-byte hash reads. The event loop polls input and Wi-Fi between steps. Metadata and destination-chapter parsing remain synchronous. Indexing advances one page per poll.

The loading page uses the selected fonts and text raster settings, the saved orientation, and the firmware display level count. It shows indexed-page progress and a cancellation instruction. The initial presentation uses the orientation/input barrier; subsequent progress refreshes occur only after the page count changes and at least two seconds have elapsed. The temporary grayscale raster is released after packing the first loading frame. A button action or tap cancels the selected book and proceeds to the library chooser when books are available, otherwise to the built-in specimen. A parse failure tries the next candidate. Cancellation recovers fonts and saved state without recording a reading position or writing the journal. The fallback specimen also indexes between polls. Input generated during fallback loading is consumed before the normal reader event loop.

Host tests cover the shared job, retry, font/state ownership, and loading-frame pixels. The [startup validation report](../tests/evidence/picco-cooperative-startup-2026-11-08.json) records controller tests and both firmware variants. Firmware builds check device integration. Physical responsiveness, display timing, wake-button behavior, and peak memory remain unqualified. Font/state loading, metadata-cache loading/saving, archive metadata parsing, and chapter parsing remain synchronous startup work.

## Cancellable library opening

Selecting a library entry opens its file handle and presents an Opening book panel before archive parsing. A matching cached size and modification time permit reuse of the content ID. Otherwise, polls hash in five-millisecond batches of 8192-byte reads and refresh the cached stamp. Metadata and destination-chapter parsing use the same file handle. Each subsequent poll indexes one page. Cancel and Back preserve the current book, page, bookmarks, and history. The destination replaces the current book only after its selected page renders. A changed reading context invalidates pending work. Cache writes are disposable; reading-state publication retains its existing atomic-file or journal requirements.

Pending opening prevents automatic device sleep. The panel has no per-page refresh, so indexing does not cause repeated e-paper updates. Background services continue between hashing and indexing steps. An external panel change discards the pending open on the next poll. Archive reading, chapter parsing, and the final page raster are synchronous. The direct uncached document-opening API hashes synchronously. Startup and menu opening use the cooperative cached path. A step can still analyze a whole paragraph and shape several candidate lines; it is a work unit, not a wall-clock deadline. Large-paragraph latency, physical cancellation responsiveness, and peak memory remain unqualified.

The controller checks the current book ID, retained source position, and layout before each opening step, including the hashing phase, and again before committing. Finishing before hashing or pagination completes returns an error without replacing the current book. Hash-phase parse errors also leave the current book available. Tests cover chunk boundaries, early finish, navigation and reflow during hashing, deferred malformed-EPUB errors, and menu cancellation during both hashing and indexing. Simulator smoke tests exercise the complete library-selection path. Physical SD latency and cancellation responsiveness remain unverified.

## Cancellable font-size changes

Typography size controls, simulator size shortcuts, and device orientation changes start a cooperative reflow job. The page stays visible while pages reflow; Back abandons the change. Each poll indexes one page. The old and pending page indexes share the parsed chapter through `Arc`, so resizing does not reread the archive or copy chapter text. The previous size, orientation, page, source position, and history remain unchanged while the job runs. Completion validates the current book, source position, previous layout, and previous orientation, renders the selected destination page, then replaces the page index, size, and orientation together. Failure or cancellation retains the previous layout. The UI returns to its prior panel, or to reading when a simulator shortcut started the job. An external panel change discards pending reflow on the next poll.

Pending reflow prevents automatic device sleep. Completion saves through the frontend's existing state store, including device journal saves when typography controls remain open. Failed device saves disable further saving and sleep; they do not roll back the already displayed size. Stroke, coverage, hinting, and fractional-position controls remain immediate raster settings. Callers of the synchronous controller reflow and rotation actions retain their synchronous path. Whole-paragraph analysis and final rasterization still have no wall-clock bound. Host tests cover cancellation, incomplete completion, stale navigation and orientation, source-position retention, and pixel equivalence with synchronous reflow in all four orientations. Physical latency and peak allocation remain unqualified.

## Updates

The first installation writes the application slot over USB with `scripts/picco-flash`. After that, the stock recovery application, which femto leaves in the factory slot, installs updates from the SD card. The stock partition table has one application slot, so an application cannot replace itself; recovery does it instead. Nothing is repartitioned.

The `Firmware update` panel has three rows: what is known (the installed version, or the version that is available or ready to install), the next step (`Check for updates`, `Download`, `Install and restart`, or the work in progress, which cannot be activated), and the `Check automatically` switch.

An update is an application image named `firmware.bin` in the `update` directory of the card. There are three ways to put one there:

- Choose `Check for updates` in the `Firmware update` panel of Settings with Wi-Fi connected. The reader fetches the manifest of the latest [release](https://github.com/eikopf/femto/releases) over HTTPS and compares its version with its own. When the release is newer the row becomes `Download` with the image's size; choosing it downloads the image to the card in the background. While the panel is open the row shows the megabytes received and a progress bar, redrawn every three seconds at most, then `Verifying the download`. The download is published as `update/firmware.bin` only if its length, SHA-256 and embedded version match the manifest; otherwise it is deleted. A connection that breaks is resumed from the bytes already on the card with an HTTP range request; the download gives up after four attempts in a row that receive nothing, and choosing `Download` again continues from the same point. Wi-Fi power saving is off while any network work is in flight (a check or download, a catalog or sync request, or an open tailnet session), because modem sleep stalled long transfers and timed out name lookups on a weak link. `Check automatically` makes the reader perform the check once after each start, as soon as Wi-Fi and the clock are ready; it never downloads by itself, and it shows the available version in the menu's status row.
- Copy the image to `update/firmware.bin` on the card with a card reader. The panel then shows the image's version as ready to install.
- Run `./scripts/picco-update [IMAGE]` with the reader connected over USB. It copies the image to the card, starts the installation, reports recovery's progress and restarts the reader. It takes about 70 seconds for a 7 MB image.

Installing saves the reading state, writes recovery's `update/.ota_pending` marker, selects the factory slot and restarts. Recovery checks the image, writes it to the application slot, removes the package and marker, selects the application slot and shows `Update complete`. Tapping `Restart` there starts the new firmware, which resumes the open book. Recovery refuses to start on battery when the charge is low and keeps the marker until an installation succeeds, so an interrupted installation starts again at the next power-on. If the application slot is ever left unbootable, recovery lists the images in `update` for manual installation, and USB flashing still works.

Femto offers only images whose application version starts with `femto-`. The version comes from `CONFIG_APP_PROJECT_VER` in `sdkconfig.defaults`; Settings shows the running version in its last row. Recovery performs the full image validation.

Release downloads use `https://github.com/eikopf/femto/releases/latest/download/`, which redirects to GitHub's asset host; every connection verifies its certificate against the built-in bundle and needs a synchronized clock. The manifest and the image come from the same place, so the hash detects a damaged download but not a compromised release. Releases are not signed.

On the tested Picco, at about -74 dBm with 8% packet loss, a check took 5 to 12 seconds and the 7.1 MB download of release 0.1.1 took 150 seconds without a retry; the image was then installed through recovery and booted. Two earlier attempts with power saving on and no resume failed after stalls of 27 and 89 seconds. ## Offline update planning

The host planner validates an unsigned candidate image against a complete flash backup without opening a serial port or generating a flash command:

```sh
nix-shell --run 'python scripts/picco-update-plan.py --backup /path/to/picco-full-flash.bin --image output/picco/femto-picco.bin --manifest output/picco/femto-picco.json' > output/picco-update-plan.json
```

The backup must contain exactly 16 MiB starting at flash offset zero. The planner reads its binary partition table at `0x8000`, verifies its MD5 record, and rejects overlapping, out-of-bounds, misaligned, duplicate-label, flagged, or unsupported partition entries. This initial profile requires the reference `app` OTA slot at `0xE0000` with size `0xE70000` and the `safeboot` factory slot at `0x20000` with size `0xC0000`. A different profile is rejected rather than inferred from filenames or build metadata. The binary table rules follow the pinned [ESP-IDF partition-table generator](https://github.com/espressif/esp-idf/blob/v5.5.1/components/partition_table/gen_esp32part.py).

The shared image validator checks segment bounds, zero padding, the segment XOR checksum, ESP32-S3 chip ID, and any appended SHA-256. Application images also require an application descriptor. The candidate requires a digest and exact length; trailing signatures or other data are unsupported. Backup images may have remaining partition bytes after the validated image prefix. The planner requires structurally valid bootloader, factory recovery, and previous application images. It therefore does not yet plan repairs from a corrupted existing application. Image parsing follows Espressif's [firmware image format](https://docs.espressif.com/projects/esptool/en/latest/esp32s3/advanced-topics/firmware-image-format.html). These integrity checks do not establish bootability or trusted provenance.

The report binds the candidate to its build manifest and records hashes of the full backup, partition table, partitions, and validated image prefixes. It describes the proposed application write and the enclosing 4096-byte erase range. Hashes cover all backup bytes outside that erase range, including recovery, bootloader, partition table, boot-selection data, and vendor data. The rollback record identifies the original complete application slot within the retained full backup. The planner emits JSON to stdout and leaves its inputs unchanged. It does not modify OTA selection data or extract credentials.

Every report sets `write_authorized` and `hardware_verified` to false. A flash dump cannot establish current eFuse security settings, chip revision, device identity, backup provenance, or an operational factory recovery path. Live checks, recovery-entry qualification, an explicit installation operation, post-write readback, and physical boot/recovery tests remain required implementation and qualification work. Flag-free plaintext partitions do not prove that secure boot or flash encryption is disabled. No installer, device read, device write, or recovery test is performed by this command.

`./scripts/check` runs synthetic backup and corruption tests. They cover image and partition-table integrity, overlap, flags, profile mismatch, backup length, required recovery images, manifest mismatch, CLI input preservation, and packaging rejection before replacing a manifest. The generated femto image also passes the shared validator and the pinned Espressif image inspector. `output/picco-update-plan-synthetic.json` is local test evidence using the compiled candidate and a synthetic backup; it is not a plan derived from a physical Picco.

## Offline readback verification

The same command accepts a complete post-write flash dump for comparison:

```sh
nix-shell --run 'python scripts/picco-update-plan.py --backup /path/to/picco-full-flash.bin --image output/picco/femto-picco.bin --manifest output/picco/femto-picco.json --readback /path/to/picco-readback.bin' > output/picco-readback-verification.json
```

The verifier recomputes the plan from the backup, candidate, and manifest. It does not accept a saved plan as authority. The readback must contain exactly 16 MiB from offset zero. Four comparisons cover the entire flash: candidate bytes, `0xFF` bytes between the candidate end and its final erase-sector boundary, and the original bytes before and after the erase range. The erased-tail requirement defines the expected write operation; an installer that restores old bytes into this tail does not satisfy this plan. Changes in any other partition, unused gap, or remaining application-slot byte fail verification.

The JSON report includes expected and actual range hashes and the first differing absolute offset in each failed range. It does not include raw flash contents. A matching readback returns exit status zero. A mismatch emits the report with `readback.matches_plan` false and returns status one. Invalid inputs return status one with a diagnostic and no JSON report. Input files remain unchanged.

File comparison establishes byte equality only. It does not establish which device supplied either dump, whether a physical write occurred, whether flash encryption is disabled, or whether the application and recovery boot. `hardware_verified` and `write_authorized` remain false. A matching dump must be captured before boot or other activity changes persistent flash data. Synthetic tests cover both ends of each compared range, invalid readback lengths, manifest rejection, CLI exit status, and input preservation. Physical readback and boot qualification remain pending.
## Cancellable chapter navigation

The device and simulator use cooperative indexing for cross-chapter contents, chapter, and bookmark selections, direct links, following previews, return from jump, and page turns at chapter boundaries. The current page or menu stays on screen meanwhile, with no progress panel; other input waits and Back abandons the move. Each poll indexes one page. The current chapter, selected page, source position, links, and back history remain unchanged until the destination index completes and its selected page rasterizes successfully. Successful completion returns to reading and records the destination through the frontend state store.

The pending job checks the book ID, source position, layout, orientation, and back history before every indexing step and before completion. Incomplete or stale jobs cannot replace the current chapter. Explicit jumps add the previous source anchor to history only at completion. Return from jump removes its history entry only at completion. Crossing a chapter boundary with a page turn does not add jump history. Backward crossing selects the preceding chapter's final page.

Pending navigation defers automatic device sleep. Destination chapter parsing and link-target resolution remain synchronous before indexing begins. The pending destination chapter is retained alongside the current chapter, so peak memory can include both parsed chapters and both compact indexes. Startup and the synchronous controller dispatch API retain synchronous indexing. Whole-paragraph analysis and final rasterization have no wall-clock deadline. Physical cancellation latency and peak memory remain unqualified.

Following a preview shares its parsed destination chapter with the pending index through `Arc`; it does not reread the chapter or copy its text. The preview and its compact index remain available during indexing, in addition to the current reading index and pending destination index. Cancel or Back restores its selected page and raster while the preview remains valid, so the reader can continue inspecting the note. If the source reader changed, the UI discards the stale preview and returns to a renderable root menu with an error. Completion releases the preview and records one return anchor. A preview page turn changes the follow target to that preview page's source location. Same-chapter links and preview follows use the existing page index immediately. Host tests cover cancellation, source-location and pixel equivalence, supplemental notes, and return history.

The Remote buttons menu edits page, arrow, and volume mappings, plus existing custom usages. Each row cycles previous, next, and off. Restore defaults and Disable all buttons apply to the complete map. Volume mappings require explicit selection. Remote input cannot operate the menu. Settings persist through the existing save-on-menu-close path. These controls do not pair or connect a remote; the configured-peer file remains required for Bluetooth input.
